# Resolve roles and preserve handoffs

Carry delegation roles into plans, checkpoints, and handoffs. Separate the role to resume, prior model history, and explicit human overrides. Record the following for each delegate, including builders and independent verifiers:

| Field | Record |
|---|---|
| Role and panel arm | Exact configured role and one-based arm to resume. |
| Previous resolution | Prior harness, model, and effort returned by the resolver. Label these as historical. |
| Previous execution | Actual prior harness, model, and effort, with the observation or receipt that establishes them. Record unknown values explicitly. |
| Human override | Original explicit human model request and its source, or that no such request is established. |

Record the coordinator's previous execution separately when available. Keep resolver output separate from actual execution, including substitutions and inherited or unknown identities. A resolved model alone does not prove which model ran.

Preserve a specific-model override with its original explicit human request. Model names in defaults, examples, past runs, or agent-written summaries do not establish such a request. If the source is unavailable, report the uncertainty instead of attributing the model choice to the human. A direct human model request still takes precedence.

On pickup, resolve the saved role for the receiving harness and its current configuration, even when the previous harness differs. Keep previous resolutions and execution identities as history, not dispatch requirements. A recovered statement such as "builders require Sonnet" establishes no override without the original human request. When a legacy handoff omits the role, recover it from the original brief or matching playbook, not the prior model name. If the role remains unknown, report that gap. Record the replacement's resolution and observed execution without overwriting the prior history.

For durable recovery, preserve the exact role and one-based panel arm, brief, standing orders, checkout, resolved identity, and any observed native task id or CLI receipt. A missing observation leaves the child's liveness unknown. It does not prove that the child stopped. To recover, spawn the saved role per **Spawn a role** like any other spawn, and use the printed arm whose `arm` matches the saved arm. Do not choose `default`, another panel arm, or a guessed model. Record the harness, model, and effort that the replacement runs on. Recovery keeps the workflow's existing retry allowance.

Retain the exact raw `--work-model` argument from the final successful resolver invocation and its complete printed arm. Keep this pair separate from observed execution identity. In an orch attempt, save it as `resolutionContext: {workModel, resolvedArm}` per the [orch reference](../../poteto-mode/scripts/orch/README.md#optional-durable-attempts). A successful invocation without the flag records `workModel: null`. An unsuccessful resolver invocation supplies no successful context. Keep legacy absence unknown. Later model substitution or effort inheritance does not rewrite the saved arm. To recover a `trail reviewer`, pass a saved string `workModel` as `--work-model`. For a saved null, omit the flag. Without saved context, pass the model the work ran on, as for a new review.

## Spawn a role

Every pstack spawn runs a role from the models config, such as `feature` or `how explorer`, sometimes under a persona. Build each spawn in this order.

1. **Name the role and the persona.** The skill or playbook step names the role. A spawn whose skill names no role uses `default`. A `subagent_type` of `poteto-agent` or `comment-sicko` in skill text names a persona, and `general-purpose` names none. Neither one picks the model or the effort.
2. **Resolve the role.** Run the resolver once per task, and again after the harness or config changes:

   ```sh
   python3 "${PSTACK_SKILLS_ROOT:?}/setup-pstack/scripts/check-models-config.py" --resolve --harness <claude-code|codex|grok|hermes> [--work-model '<model>@<effort>'] [<role>...]
   ```

   Failure signal: nonzero exit. It prints one JSON line per arm with `model`, `effort`, and `source`, and a `notes` list when the resolver has a warning. Relay each note to the user in the reply. Pass the roles the skill names, or none to print every role. Run it from the project root or pass `--project <root>`. Do not read the config files to pick values. The rules, and the grammar for editing the files, live in setup-pstack's [models config reference](../../setup-pstack/references/models-config.md). When you resolve `trail reviewer`, pass `--work-model '<model>@<effort>'` with the model and effort that did the work, and use the printed arm. Quote the value, because zsh expands the `[1m]` in `opus[1m]@xhigh` before the resolver runs. When the work's role resolved to `inherit-parent`, pass the session model. When an arm's note says to pass the session model, you passed `auto` or `inherit-parent`, which name no model. Rerun with the session model, the model ID your system prompt or this CLI's config names, and use that run's arm. If you cannot tell the session model, keep the printed arm and disclose the execution identity per step 5. Pass the model the work ran on, as the role's resolved value or the CLI's own model ID. A full Claude ID such as `claude-opus-5-5` maps to its alias on a CLI that takes aliases, and stays a literal slug on Hermes. On Claude Code, a work model that is not a Claude alias, a Claude ID, `auto`, or `inherit-parent` exits 2. On another CLI, a work model that CLI cannot use adds a note and applies no step. When the exit 2 names `--work-model`, correct the value and rerun. Drop a `[1m]` suffix from a Claude alias, or the provider prefix and tag from a slug such as `anthropic/claude-opus-4.7`. If the work ran on another vendor's model, rerun without the flag: every Claude Code arm is a Claude model, so the printed arm is cross-model. Otherwise rerun without the flag and disclose the execution identity per step 5. With the reviewer unpinned, the resolver prefers a different model in the work model's family that the user's config allows, a higher tier first, and adjusts the effort. A `"step": "same-model"` field means the config allows no other model in the work model's family, or the user pinned the reviewer with `trail reviewer step: off`. Report that resolution and disclose the execution identity per step 5. Every model you pass comes from this output or an explicit request in the task. Never improvise one, and say which role each model came from. If the resolver exits nonzero or cannot run, still spawn the role. Omit the model and effort so the child inherits the session's. For `trail reviewer`, disclose the execution identity per step 5. For a panel role, keep the arm count that the panel's skill names as its default, and brief each arm the way that skill says. Report the resolver error and the values the child ran on. Never drop a spawn because the resolver failed.
3. **Build the spawn call for this CLI.** Use the current runtime adapter selected in [pstack-harness](../SKILL.md#runtime-adapters). `inherit-parent` in a field means omit that field.
4. **Brief the persona.** A persona that runs as a briefing gets its complete text from the [persona contract](named-roles.md). Never summarize it.
5. **Report execution without dropping an arm.** Apply this step to every spawn, including a `trail reviewer` that normally resolves to `inherit-parent` without a fallback or `step` marker. If the spawn rejects a model, or a spawned arm fails on model availability such as exhausted usage credits, omit the model, let the arm inherit the session model, and report the substitution. Label the verdict and reply `same-model` when the observed reviewer and work models match. When either identity is unknown, say the review may be same-model. For explicitly requested models, use the **arena** skill's [required-arm rule](../../arena/SKILL.md#required-arms). If no field or agent can carry the effort, the effort alone becomes `inherit-parent`. Keep the model and the arm. Say in the reply which role's effort was inherited and why, such as "`how explainer` ran at the session effort because `pstack-effort-xhigh` is not loaded. Run `/setup-pstack` to register it." When a persona ran as a briefing in an effort agent's prompt instead of under its native name, say that too. Delegates return resolver notes and actual or inherited model and effort observations to the parent, including substitutions, limitations, and unknown values. The parent relays them in its reply.

## Fork restrictions

A fork, such as Claude Code's `fork` agent type or a Codex full-history fork, inherits the lead's whole context and runs on the lead's model and effort, ignoring any override. Fork only when the role resolves to `inherit-parent` for both, as `default` ships, and the brief would otherwise restate context the lead already holds, such as drafting from files the lead just read or writing a resume note. Never fork a verdict, a review, or a role that resolves to a model or an effort. A fork returns the same thin report as any spawn, per **principle-guard-the-context-window**.
