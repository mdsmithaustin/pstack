# Spawn, isolate, and report subagents

**Spawn a subagent.** In order of preference:

1. Your harness's native subagent or delegation tool, whatever it is called.
2. No such tool → invoke your own CLI non-interactively as a subprocess (its help names the command and flags), one invocation per arm, run concurrently in background shells, each arm's report collected from stdout or a file path named in its brief.
3. No subprocesses either → run the arms sequentially inline, one at a time, each writing its report to a file before the next starts, then synthesize. Keep the configured arm count. A verdict or review that runs inline is not independent. Label it `self-review` in the verdict and in the reply, and never count it as an independent verdict.

Each writer gets its own git worktree, whichever mechanism spawns it. When the brief names no commit and `git -C <project> rev-parse --verify -q 'HEAD^{commit}'` prints nothing, make no worktree and use the fallback below. Keep the location a native isolation option picks when the option makes a git worktree, that is, when `git -C <its path> rev-parse --path-format=absolute --git-common-dir` prints the project's. When you run `git worktree add` yourself, make one worktree at a time, and never place the worktree beside the repository:

- A throwaway checkout (verify, review, replay, eval arm, arena candidate) goes under `mktemp -d "${TMPDIR:-/tmp}/pstack-<slug>.XXXXXX"`. Remove it with `git worktree remove` when its run ends.
- A worktree that holds unpushed work goes under `.worktrees/<slug>` in the main checkout. If the repository does not ignore `.worktrees/`, append it to `"$(git rev-parse --git-common-dir)/info/exclude"` first.

**Remove a writer's worktree.** A throwaway checkout follows its own rule above. Act only on a worktree that your own record ties to the ID of the writer run you made it for, such as a spawn result or Autopilot's `children.tsv`. Never act on `git worktree list` alone, and if you no longer have that record, remove no worktree. Start only when your harness reports that every run your record lists at that path has ended:

1. Run `git fetch --prune origin`, then [`worktree-audit.sh`](../../poteto-mode/scripts/worktree-audit.sh) `-b <your branch>`. Keep the worktree unless the audit exits 0 and prints a row for it whose `DIRTY` reads `clean`. Ignore its `BUCKET`.
2. Remove the writer's worktree if its work is merged into your branch, you abandoned the work, or the audit shows its `REMOTE` as `pushed`. First run the checks in steps 4 and 5 of [Worktree and simulator cleanup](../../poteto-mode/playbooks/worktree-cleanup.md), and save any commit that step 4 finds on no branch with `git branch <name> <sha>`. If that save fails, keep the worktree.
3. Run `git worktree remove <path>` without `--force`. Keep the worktree if git refuses or if a check fails or asks for a decision. Never run `git worktree prune`, step 5's included, because it also deletes the records of other worktrees whose directories are missing.
4. Delete the writer's branch only with `git merge-base --is-ancestor refs/heads/<branch> refs/heads/<your branch> && git branch -d <branch>`. If you have no branch of your own, as on a detached `HEAD`, keep every writer branch.
5. Name in your reply each worktree and branch from your record that you keep, and each branch that you saved in step 2.

If `git worktree add` fails or `HEAD` does not resolve, give each writer whose output the lead collects from a directory, such as an arena candidate or a verify arm, its own plain directory for each commit its brief names, or one directory when the brief names none. A verify arm whose brief names a parent and a head gets two. Use the directory its skill names, or a fresh `mktemp -d "${TMPDIR:-/tmp}/pstack-<slug>.XXXXXX"` for each. When the writer needs the project's files, resolve every named commit, or `HEAD` when the brief names none, with `git -C <project> rev-parse --verify -q "<commit>^{commit}"` before you seed any directory. If a named commit prints nothing, run `git -C <project> fetch origin <commit>` and resolve again. If it is still missing, report the writer blocked and seed none of its directories. Never seed a different commit in its place. If the brief names no commit and `HEAD` prints nothing, the project is not a git repository or has no commit yet, so seed from a snapshot repository as below. Otherwise seed each directory with `git clone -q --no-checkout --shared <project> <dir> && git -C <dir> checkout -q --detach <sha>`, where `<sha>` is what its own commit resolved to. Its brief names each directory and its SHA, says to work only in those directories, and says to leave the checkout unchanged. These writers can run at the same time. Delete each directory when its run ends, after you take its output. A writer whose work must land on the checkout's branch runs in the current checkout, one at a time. Never take the writer's work back into the lead.

**Snapshot repository.** Copy the project's working tree into `snapshot/` inside the run's scratch directory, or inside a fresh `mktemp -d "${TMPDIR:-/tmp}/pstack-<slug>.XXXXXX"` when the skill names none. Leave out `.git` and every dependency, build, and cache directory at any depth, such as `node_modules`, `.venv`, `target`, `dist`, `__pycache__`, and `.pytest_cache`. Commit the copy with `git -C <snapshot> init -q && git -C <snapshot> add -A && git -C <snapshot> -c user.name=pstack -c user.email=pstack@localhost -c commit.gpgsign=false -c core.hooksPath=/dev/null commit -q --no-verify --allow-empty -m snapshot`. Seed each directory with the clone command above, using `<snapshot>` as `<project>` and its commit as `<sha>`. Never run `git init` or commit in the user's project to unblock delegation. To land a writer's changes in the project, run `git apply` there on the patch that `git -C <dir> add -A && git -C <dir> diff --cached --binary <sha> -- . ':(exclude,glob)**/node_modules/**'` prints, with one `':(exclude,glob)**/<name>/**'` for each directory name the copy left out. Keep the patch to the files the writer meant to change. Delete the snapshot with the directories.

**Parallelism.** Real where the mechanism allows it (independent tool calls in one message, concurrent subprocesses); otherwise sequential with the same arm count.

**Read-only.** Leave the original checkout unchanged. A read-only role that runs tests, builds, linters, package runners, or other commands gets a throwaway checkout under `mktemp -d`, as defined above. When the brief names no commit and `HEAD` does not resolve, seed it from a snapshot repository instead of the dirty-input steps below. Tools can write caches, coverage, environments, and generated files even when the agent edits no source. Bind that checkout to the exact reviewed input, including authorized relevant uncommitted content. Name the throwaway path as the only place to run those commands. Pure source inspection can use the original checkout. Leave generated state in the throwaway checkout instead of restoring files in the original. Use an enforcing option when it permits the required verification there. Otherwise state the original-checkout boundary plainly in the brief.

For dirty reviewed inputs, record the original `HEAD`, `git status --porcelain=v1 --untracked-files=all`, and the bytes of the explicitly named relevant files. Capture the authorized tracked changes with `git diff --binary HEAD -- <authorized tracked paths>`, saving the patch outside the original checkout. Seed the disposable checkout at that recorded `HEAD`, then apply the patch there with `git -C <throwaway> apply <patch>`. Copy only the explicitly named relevant untracked files into the same relative paths there. Before executing verification commands, compare the disposable tracked diff and relevant file bytes with the reviewed snapshot, including deletions and untracked files. Confirm that the original file bytes and Git status still match the recorded snapshot. If inputs changed during transfer, capture the reviewed snapshot again before running commands. Preserve the original checkout throughout; do not run cleanup restores there.


- **Panels keep their configured arm count.** Run a three-model panel as three arms even in a one-model harness. Brief each arm the way the panel's skill says, and run the arms in parallel or sequentially. For exact model requests, apply [role resolution step 5](roles.md#spawn-a-role) and its linked required-arm rule.

- **Honesty**: never report parallel arms that actually ran sequentially; name the mechanism used. Wherever a rule labels a review same-model or `self-review`, put the label in the verdict and in the reply.
