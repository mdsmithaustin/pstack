### Multi-phase or multi-PR plan

**You own the plan, not the code. The plan is a checklist an owner runs box by box and the operator audits from the evidence.** The plan is the deliverable. Do not implement.

Read this playbook in full.

1. When the change is one or two files with an obvious approach, decide to skip the plan.
2. Settle open questions by prototype before you write, per `playbooks/prototype.md`. Ask the operator only about a product or preference call that no run can settle. If step 1 decided to skip the plan, skip this step.
3. Write the plan file. Open with what changes, the source spec, issue, or task text by path, the PR ids in landing order, and the dependency graph, which says which PRs are independent and branch from trunk, which wait for which, and the files each may touch. Every owner brief points at that source, not at the plan's summary of it. Preserve the accepted scope per [Prove It Works](../../principle-prove-it-works/SKILL.md). Then one section per PR. One PR is one change with its own evidence. Call the Skill tool with `principle-sequence-verifiable-units`. Each section has checkboxes for what it depends on, the files it edits, the one change it builds, the result you see, and its verification. It also has a box for deslop's **Before each commit** check with evidence before every commit, and, in a gated repository, a box to open the PR through Opening a PR's **Gated publish** section. If step 1 decided to skip the plan, skip this step.
4. Tests alone are not sufficient verification. A PR is verified only when its unit, live, and perf boxes are all checked. Each live box drives the real surface with a concrete scenario and a pass predicate. The perf box names the metric, the probe, the trunk baseline measured first, and the number that fails. A PR that changes an interaction waits for the operator's review before merge. The owner rebases onto current trunk before the code-ready report. After the first full swarm, a rebase, a conflict resolution, or a minor fix gets a single verifier per `playbooks/autopilot-full.md` step 4. A true finding that does not block becomes a follow-up issue, except a security, privacy, auth, data, or permission-boundary finding, which goes to the operator directly. If step 1 decided to skip the plan, skip this step.
5. Hand back the plan path and stop. Execution starts on the operator's explicit go. If step 1 decided to skip the plan, skip this step.

**Reply:** the plan path, the PR ids with their dependencies and the review-gated set, and what stays unproven. When step 1 decided to skip the plan, end the turn with a reply that says why the change needs no plan and names the playbook that fits it, such as Feature or Bug fix. Implement nothing. That playbook starts on the operator's go.
