### Code review

**You own the verdict.** This playbook reviews someone else's pull request, branch, or diff. The deliverable is findings, not edits. Do not push to the author's branch. Your own PR goes through **Opening a PR** and **Babysit** instead.

Steps 3 to 6 are design checks. Each names the principle skill that governs it. Use that skill before the step, and open [`../references/review-lens.md`](../references/review-lens.md) for the questions, the evidence each one needs, and when to leave it.

1. **Intent known.** The change's purpose is stated in one sentence, and every behavior change nobody asked for is a finding. Diff the head against its merge base with `git diff <base>...<head>` or `gh pr diff <number> -R <host>/<owner>/<repo>`, with `<host>/<owner>/<repo>` from origin's fetch URL. Read the PR description, the linked issue, and the commit messages. Judge the execution against that intent. An unclear intent is itself a finding. Call the Skill tool with `principle-redesign-from-first-principles`, and open the lens's [Unrequested behavior changes](../references/review-lens.md#unrequested-behavior-changes-principle-redesign-from-first-principles) section. Flag each behavior change that no sentence in the description, issue, or spec asks for. Run `python3 "${PSTACK_SKILLS_ROOT:?}/pstack-harness/scripts/preserve.py" --since <base> --report-only` in the head checkout: a test that existed at the base and now fails, or was edited by the change with no sentence in the description explaining why, is a finding.
2. **Subsystem understood.** You have read the whole changed files and the callers of what changed, not only the hunks. Apply the review lens's [Accumulated complexity](../references/review-lens.md#accumulated-complexity) check to extended units and record its structural verdict. For a change across modules, call the Skill tool with `how` on the touched code before you judge it.
3. **Vocabulary checked.** No concept gained a second name, no type carries two meanings, and no two types with different callers were merged. Call the Skill tool with `principle-model-the-domain`. Grep each new name and the older term it may duplicate.
4. **Boundaries checked.** No domain or policy module imports a framework, driver, ORM, IO library, generated schema, or adapter, and no wire type leaks through a public surface. Call the Skill tool with `principle-boundary-discipline`. Read the import list of every changed domain or policy module. Flag validation added deep inside typed code.
5. **Callers checked.** Every change to a shared function, type, or constant is safe for each caller outside the PR's intent. Call the Skill tool with `principle-model-the-domain`. List the callers and read each one. Flag a behavior change that reaches a caller serving a different business function. The fix direction is to fork the piece for the requester.
6. **Tests checked.** Each behavior the PR changes maps to a test that fails on the base, and each test asserts behavior rather than internals. Call the Skill tool with `principle-test-behavior-not-implementation`. Run its two imagined edits, break the behavior and change the internals, on every new or changed test. A behavior change with no such test is a finding.
7. **Correctness checked.** Each changed path has been traced for edge cases, error handling, ordering, concurrency, and security. Then read [`code-quality-review.md`](../../interrogate/references/code-quality-review.md) in full and apply its structural lens. For a large or contested change, also call the Skill tool with `interrogate` for a multi-model pass.
8. **Slop checked.** The aggregate diff has been through the deslop rules, with the full-read evidence and the reviewed base and head recorded. Call the Skill tool with `deslop` in review-only mode and open the [Deslop review lens](../references/review-lens.md#deslop). Read its complete `SKILL.md`, including every rule and the Report section. Recover any omitted or truncated content before continuing. Apply its rules to the aggregate diff at the reviewed base and head, not only the latest commit. Keep this playbook's read-only boundary. Report cleanup findings by rule ID and location for the author to fix. Inspect any supplied cleanup evidence against the actual diff. Return a justified no-change result when no rule requires a cut, or `no code` with the inspected paths. Repeat the pass after fixes, a rebase, or a base change before issuing an updated verdict. This pass supplements the author's per-commit checks.
9. **Restrained.** Every remaining finding survives its leave-it condition in the lens. Do not flag look-alike code as duplication without evidence that the copies change for the same reasons. Do not demand an abstraction, layer, or helper that a one-caller change does not need. Call the Skill tool with `principle-laziness-protocol`. Call the Skill tool with `principle-minimize-reader-load`. A preference is not a finding.
10. **Written.** Each finding has a severity, a location, the problem with its evidence, and a fix direction, and the verdict follows from them. Severity is `critical`, `warning`, or `nit`. Location is `file:line` or a symbol. Order them by severity. Name the principle behind each design finding. Include the deslop result and its evidence. An incomplete deslop pass prevents an approve verdict. Post to the PR only when the user asked for it. Even then, give security, privacy, auth, data, and permission-boundary findings to the user directly and leave them out of the post.

**Reply:** the intent in one sentence, a verdict (approve, request changes, or comment), the findings in severity order, the principle behind each design finding, the deslop result with its reviewed base, head, and evidence, and what you checked and found clean. State any incomplete read or verification gap.
