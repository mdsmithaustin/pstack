### Code review

**You own the verdict. Read the change, judge the design, report findings.** This playbook reviews someone else's pull request, branch, or diff. The deliverable is findings, not edits. Do not push to the author's branch. Your own PR goes through **Opening a PR** and **Babysit** instead.

Steps 3 to 6 are design checks. Each names the principle skill that governs it. Read that leaf before the step, and open [`references/review-lens.md`](../references/review-lens.md) for the questions, the evidence each one needs, and when to leave it.

1. **Establish the change and its intent.** Diff the head against its merge base with `git diff <base>...<head>` or `gh pr diff <number>`. Read the PR description, the linked issue, and the commit messages. State the intent in one sentence. Judge the execution against that intent. An unclear intent is itself a finding.
2. **Understand the affected subsystem.** Read the whole changed files, not only the hunks, and the callers of what changed. For a change across modules, run the **how** skill over the touched code before you judge it.
3. **Check vocabulary and concepts.** Apply **principle-model-the-domain**. Grep each new name and the older term it may duplicate. Flag a second name for a concept the code already names. Flag one type that now carries two meanings, and two types merged when their callers use them differently.
4. **Check module boundaries and dependency direction.** Apply **principle-boundary-discipline**. Read the import list of every changed domain or policy module. Flag an import of a framework, driver, ORM, IO library, generated schema, or adapter module. Flag validation added deep inside typed code and wire types that leak through a public surface.
5. **Check shared code against its other callers.** Apply **principle-model-the-domain**. Before you judge a change to a shared function, type, or constant, list its callers and read each one outside the PR's intent. Flag a behavior change that reaches a caller serving a different business function. The fix direction is to fork the piece for the requester.
6. **Check test quality.** Apply **principle-test-behavior-not-implementation**. Run its `undefined` check on every new or changed test. Map each behavior the PR changes to a test that fails on the base. A behavior change with no such test is a finding.
7. **Check correctness and local bugs.** Trace each changed path for edge cases, error handling, ordering, concurrency, and security. Then apply the structural lens in the **interrogate** skill's [`code-quality-review.md`](../../interrogate/references/code-quality-review.md). For a large or contested change, also run the **interrogate** skill for a multi-model pass.
8. **Apply restraint.** Drop each candidate finding that meets its leave-it condition in the lens. Do not flag look-alike code as duplication without evidence that the copies change for the same reasons. Do not demand an abstraction, layer, or helper that a one-caller change does not need (**principle-laziness-protocol**, **principle-minimize-reader-load**). A preference is not a finding.
9. **Write the findings.** Each finding has a severity (`critical`, `warning`, or `nit`), a location as `file:line` or a symbol, the problem with its evidence, and a fix direction. Order them by severity. Name the principle behind each design finding. Post to the PR only when the user asked for it.

**Reply:** the intent in one sentence, a verdict (approve, request changes, or comment), the findings in severity order, the principle behind each design finding, and what you checked and found clean.
