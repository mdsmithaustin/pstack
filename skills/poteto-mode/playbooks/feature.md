### Feature

**You own the design. Plan, review, verify.** Each step opens with the outcome that must hold before the next step starts. Use step 6 to decide who implements.

1. **Preserved (`how`).** Everything the task does not explicitly change still behaves as it does today, and the step records what that is, with the start commit. Call the Skill tool with `how`, and ask it to list the components, hooks, helpers, and UI patterns the repository already has for this job, and the inputs the program accepts today. Reuse them in the design and in every brief. Extend a shared one only when every caller keeps its behavior. Give the reason for each new one. The current code's behavior is the spec for everything the task does not explicitly change. Every input an earlier version accepted is part of that behavior. A new rejection needs a requirement you can quote from the spec; without one, accept the input. Call the Skill tool with `principle-redesign-from-first-principles`. In an empty or new project, record `no existing code` as the outcome and keep the step `completed`.
2. **Shaped (`principle-model-the-domain`).** The data shape is named, with the structure that organizes it, before any logic is written. Call the Skill tool with `principle-model-the-domain` to choose that structure. Record in the worklist item the named data shape and its organizing structure, a state machine over scattered booleans, a table/registry over branching, a typed model over repeated shape assumptions, chosen before the delegate writes logic. Every brief in step 6 carries it.
3. **Designed (`architect`).** The shape of the change is chosen, and when the change crosses a function boundary or admits several valid shapes, the alternatives were compared before any code. Call the Skill tool with `architect` for that comparison. A small, self-contained change keeps this step with `skipped: <reason>`.
4. **Specified (`spec-probes`).** Acceptance tests exist for every new requirement, each traceable to the spec, and every edge the spec leaves open is listed as a gap rather than decided in a test. When the spec gives worked examples or stated formats, write tests from them, yourself or through a test delegate on the `feature` role whose brief names the source spec by path and adds none of your reading of it. When a spec example first appears, worked or illustrative, copy its input and expected output verbatim, unused fields included, into a fixture file that tests load and later changes never edit. A later change that fails such a fixture reports the conflict in the reply, with both spec sentences, and leaves the fixture alone. Then call the Skill tool with `spec-probes` and follow its edge probe on each new requirement. List the edges its data shape raises from that skill's table, such as boundary values, empty input, ordering, and encoding. Settle each edge from the spec text, or from the current code's behavior when the spec is silent. Test each settled edge, or dismiss it with a reason when no test fits. Record each edge that neither settles as an open gap in the reply, not as a test.
5. **Planned (`principle-separate-before-serializing-shared-state`).** The work is split before anyone builds: gates before fan-out, independent streams named, shared writes separated, the smallest safe decomposition chosen. Write the throughput checkpoint as four items in the same worklist. A dimension that does not apply (single file, no fan-out) still gets its item, marked `skipped: <reason>`:
   - **Blocking first steps.** Gates run before fan-out.
   - **Independent workstreams.** Disjoint files, services, or layers parallelize. Shared writes serialize.
   - **Shared mutable state.** Default to splitting the target. Call the Skill tool with `principle-separate-before-serializing-shared-state`. Serialize only for real invariants.
   - **Smallest safe decomposition.** If one worker is best, name why.
6. **Built.** The step 4 tests pass on the integrated result, and the start commit's tests pass unedited against the new code. Run `python3 "${PSTACK_SKILLS_ROOT:?}/pstack-harness/scripts/preserve.py" --since <start commit>`. For each failure, either fix the code, or quote in the reply the spec sentence that requires the new behavior and then update the test. Built stays open until every failure has one or the other. Before implementation, record the planned hand-edited file count and independent workstream count in the worklist. Include tests and documentation. Exclude generated files and lockfiles. Delegate implementation when the plan changes **three or more files** or contains **two or more independent workstreams**. Otherwise implement directly and record the counts and the reason the work is one workstream. This cutoff is a workflow default, not a measured optimum. It overrides the harness's own spawn guidance in both directions. When a higher-priority instruction or a tool limit prevents a spawn, own the diff and record the limit.
   To delegate, read [delegation](../references/delegation.md). Call the Skill tool with `pstack-harness`, then follow its **Spawn a role** section to resolve the `feature` role. Each brief carries a specific scope: file paths, the step 2 shape and structure, the step 4 tests copied into the delegate's worktree and named as success criteria, and the step 5 workstream it owns. Disjoint file sets get one delegate each, spawned in one message. Coupled work gets one owner whose brief names the split it may make. When the implementation admits multiple valid shapes, call the Skill tool with `arena` to delegate instead, so the runners surface the alternatives and the cross-judge guards the pick. A delegate never writes the only test of its own code. Review every delegate's diff yourself.
   Unless the user said not to commit, commit the tests with the code that passes them, so no commit holds tests its code fails. In an existing repository, commit on a branch off trunk, never on trunk itself. Put both instructions in the brief.
7. **Proven (`principle-prove-it-works`).** The integrated result works on the surface the user will use, and every departure from the code around it is named. Call the Skill tool with `principle-prove-it-works`. Verify against the accepted scope and integrated result. "Inconclusive" or wrong-surface is not a pass. Flag it.
   Then check the integrated diff against the existing code for departures. Look for:
   - a new component, hook, helper or test helper where one already does the job;
   - a hand-built version of a shared UI piece;
   - a visual choice that differs from nearby screens, such as button variant, row layout, spacing, color or empty/error/loading state;
   - a show/hide or focus behavior that differs from what the replaced or neighboring UI did.

   Search the repository for each. An existing pattern records an earlier taste decision, so overruling one has to be visible. If the design is contested, call the Skill tool with `interrogate` before shipping.
8. **Landed (`principle-sequence-verifiable-units`).** The change sits in small, ordered commits on a branch, each one green on its own. Call the Skill tool with `principle-sequence-verifiable-units`, building, verifying, and committing each small unit before the next. Rebase into that order. Stack follow-ups. Keep the step 6 branch, per the **Worktree** rule in `playbooks/opening-a-pr.md`. If the project has no git repository, run `git init` in the directory that holds the project's files, and commit on its first branch.
9. **Published.** The branch is where the team reviews changes. Run **Opening a PR**. If the task has no commits to propose, or the repository has no remote, mark this step `skipped: <reason>`.

**Reply:** what you built, what you chose and why, the throughput checkpoint, open decisions, and **Departures from existing patterns**. For each departure, give the pattern it overrules, where that pattern lives, and why the change overrules it, or write None. Carry the same section into the PR body. Tables for design alternatives.
