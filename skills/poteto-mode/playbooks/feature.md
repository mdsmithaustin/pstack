### Feature

**You own the design. Plan, review, verify.** Use step 4 to decide who implements.

Run every step in order. Skip a step only as the Playbooks paragraph of the poteto-mode skill allows, and mark it `skipped: <reason>` with a reason that covers that step alone. Where a step says how to run in a new project, run it that way instead of skipping it.

1. `how` over the affected subsystem. Call the Skill tool with `how`, and ask it to list the components, hooks, helpers, and UI patterns the repository already has for this job. Reuse them in the design and the step 4 brief. Extend a shared one only when every caller keeps its behavior. Give the reason for each new one. Reuse covers structure. Another field's rejection does not carry over to a new field, because step 4 needs a requirement for each new rejection. The current code's behavior is the spec for everything the task does not explicitly change. Call the Skill tool with `principle-redesign-from-first-principles`. Keep that behavior, and say so in the step 4 brief. In an empty or new project, run the step anyway and record `no existing code` as its outcome.
2. `architect` for feature design exploration when the change crosses two or more source files and admits several plausible shapes. Call the Skill tool with `architect` for it. A small, self-contained change, or one with a single plausible shape, keeps this step with `skipped: <reason>`.
3. Write the throughput checkpoint as four items in the same worklist. A dimension that does not apply (single file, no fan-out) still gets its item, marked `skipped: <reason>`:
   - **Blocking first steps.** Gates run before fan-out.
   - **Independent workstreams.** Disjoint files, services, or layers parallelize. Shared writes serialize.
   - **Shared mutable state.** Default to splitting the target. Call the Skill tool with `principle-separate-before-serializing-shared-state`. Serialize only for real invariants.
   - **Smallest safe decomposition.** If one worker is best, name why.
4. Before implementation, record the planned source file count and independent workstream count in the worklist. Count only the hand-written source files that implement the change. Do not count tests, documentation, dependency manifests, or ignore files. Delegate implementation when the plan changes **three or more source files** or contains **two or more independent workstreams**. Otherwise implement directly and close this item with `skipped: implementation delegation below threshold`, the counts, and the reason the work is one workstream. This cutoff is a workflow default, not a measured optimum. If scope crosses the threshold, record the revised counts and delegate the remaining work. Keep the counts tied to the accepted scope, rather than splitting or combining work to avoid delegation.
   This threshold replaces advisory harness spawn guidance in both directions. Follow higher-priority instructions and actual tool limits. When either prevents a required spawn, own the diff directly with the same review separation and record `skipped: <specific prohibition or capability limit>` on this item. Close a delegated item with the implementation artifact and its reviewed result.
   Settle the acceptance tests and specification edges below for either path. For delegation, assign a subagent on the `feature` role with a specific scope (file paths, named data shape and its organizing structure, a state machine over scattered booleans, a table/registry over branching, a typed model over repeated shape assumptions, chosen before the delegate writes logic, and success criteria). Call the Skill tool with `principle-model-the-domain` to choose that structure. Before the first implementation spawn, settle the acceptance tests. When the spec gives worked examples or stated formats, write tests from them, yourself or through a test delegate on the `feature` role whose brief names the source spec by path and adds none of your reading of it. Then call the Skill tool with `spec-probes` and follow its edge probe on each new requirement. List the edges its data shape raises from that skill's table, such as boundary values, empty input, ordering, and encoding. Settle each edge from the spec text, or from the current code's behavior when the spec is silent. A new rejection, error, or reinterpretation of input needs a requirement that states it, even on a new field. Run each new rejection in the tests against the inputs the previous version accepted. Those include existing fixtures, documented examples, and earlier configs. Before you close this step, run the same check on each new rejection in the implementation. If one of those inputs now fails, drop the rejection or name the requirement that states it. Test each settled edge, or dismiss it with a reason when no test fits. Record each edge that neither settles as an open gap in the reply, not as a test. Copy the tests into each implementation delegate's worktree before it starts, and name them in the brief as success criteria. Unless the user said not to commit, commit them with the code that passes them, so no commit holds tests its code fails. A delegate never writes the only test of its own code. Call the Skill tool with `pstack-harness`, then follow its **Spawn a role** section to resolve the role. Carry the checkpoint's independent workstreams into the briefs. Disjoint file sets get one delegate each, spawned at this level in one message. Coupled work gets one owner whose brief names the split it may make. When the implementation admits multiple valid shapes (error handling, abstraction layer, test structure), call the Skill tool with `arena` to delegate instead, so the runners surface the alternatives and the cross-judge guards the pick. No "standing by" reply that waits on a nested agent. Comments per **Comments**. Surgical edits, re-ground against the source for upstream-derived files. Port shared-primitive improvements to all consumers and verify each. Commit liberally, unless the user said not to commit. In an existing repository, commit on a branch off trunk, never on trunk itself. Put both instructions in the brief.
   Parent-level fan-out also covers slices that produce independent artifacts (audits, cross-subsystem investigations, competing experiments). Rewrite the checkpoint at phase boundaries. A phase boundary gets a fresh delegate with consolidated scope, never a resume of the last one.
5. Verify on the matching surface against the accepted scope and integrated result, per [Prove It Works](../../principle-prove-it-works/SKILL.md). "Inconclusive" or wrong-surface is not a pass. Flag it.
   Then check the integrated diff against the existing code for departures. Look for:
   - a new component, hook, helper or test helper where one already does the job;
   - a hand-built version of a shared UI piece;
   - a visual choice that differs from nearby screens, such as button variant, row layout, spacing, color or empty/error/loading state;
   - a show/hide or focus behavior that differs from what the replaced or neighboring UI did.

   Search the repository for each. An existing pattern records an earlier taste decision, so overruling one has to be visible.
6. Rebase into small, ordered commits. Stack follow-ups. Keep the step 4 branch, per the **Worktree** rule in `playbooks/opening-a-pr.md`. If the project has no git repository, run `git init` in the directory that holds the project's files, and commit on its first branch.
   Call the Skill tool with `principle-sequence-verifiable-units`, building, verifying, and committing each small unit before the next.
7. If the design is contested, call the Skill tool with `interrogate` before shipping. Otherwise mark this step `skipped: <reason>`.
8. Run **Opening a PR**. If the task has no commits to propose, or the repository has no remote, mark this step `skipped: <reason>`.

**Reply:** what you built, what you chose and why, the throughput checkpoint, open decisions, and **Departures from existing patterns**. For each departure, give the pattern it overrules, where that pattern lives, and why the change overrules it, or write None. Carry the same section into the PR body. Tables for design alternatives.
