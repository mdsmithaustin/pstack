### Feature

**You own the design. Plan, review, verify.** Each step opens with the outcome that must hold before the next step starts. Use step 6 to decide who implements. Skip a step only as the Playbooks paragraph of the poteto-mode skill allows, and mark it `skipped: <reason>` with a reason that covers that step alone. Where a step says how to run in a new project, run it that way instead of skipping it.

1. **Preserved (`how`).** Everything the task does not explicitly change still behaves as it does today, and the step records what that is, with the start commit. Call the Skill tool with `how`, and ask it to list the components, hooks, helpers, and UI patterns the repository already has for this job, and the inputs the program accepts today. Reuse them in the design and in every brief. Extend a shared one only when every caller keeps its behavior. Give the reason for each new one. Reuse covers structure. Another field's rejection does not carry over to a new field; step 4 needs a requirement for each new rejection. The current code's behavior is the spec for everything the task does not explicitly change. Every input an earlier version accepted is part of that behavior. A new rejection needs a requirement you can quote from the spec; without one, accept the input. Call the Skill tool with `principle-redesign-from-first-principles`. Fit the new requirement into the design as if it had been there from day one, with no compatibility branch beside the old path. Apply the review lens's [Accumulated complexity](../references/review-lens.md#accumulated-complexity) check before extending an existing unit. Carry its history evidence and design decision into Proven. In an empty or new project, record `no existing code` as the outcome and keep the step `completed`.
2. **Shaped (`principle-model-the-domain`).** The data shape is named, with the structure that organizes it, before any logic is written. Call the Skill tool with `principle-model-the-domain` to choose that structure. Record in the worklist item the named data shape and its organizing structure, a state machine over scattered booleans, a table/registry over branching, a typed model over repeated shape assumptions, chosen before the delegate writes logic. Every brief in step 6 carries it. Boring code stays when the shape is already clear and local. An abstraction that adds indirection without deleting a branch, a duplicated rule, or an invalid state is a smell, and so is a feature that grows an if/else chain by one more branch or adds a second boolean that must stay in sync with the first.
3. **Designed (`architect`).** The shape of the change is chosen, and when the change crosses two or more source files and admits several plausible shapes, the alternatives were compared before any code. Call the Skill tool with `architect` for that comparison. A small, self-contained change, or one with a single plausible shape, keeps this step with `skipped: <reason>`.
4. **Specified (`spec-probes`).** Acceptance tests exist for every new requirement, each traceable to the spec, and every edge the spec leaves open is listed as a gap rather than decided in a test. When the spec gives worked examples or stated formats, write tests from them, yourself or through a test delegate on the `feature` role whose brief names the source spec by path and adds none of your reading of it. When a spec example first appears, worked or illustrative, copy its input and expected output verbatim, unused fields included, into a fixture file that tests load and later changes never edit. A later change that fails such a fixture reports the conflict in the reply, with both spec sentences, and leaves the fixture alone. Then call the Skill tool with `spec-probes` and follow its edge probe on each new requirement. List the edges its data shape raises from that skill's table, such as boundary values, empty input, ordering, and encoding. Settle each edge from the spec text, or from the current code's behavior when the spec is silent. When the spec defines two similar terms differently, a test fails whichever term is implemented like the other. Each test cites the spec sentence it checks or the current behavior it keeps. Text you add to the spec during the task settles no edge, and no test cites it. A new rejection, error, or reinterpretation of input needs a requirement that states the restriction, even on a new field. Run each new rejection in the tests against the inputs the previous version accepted: existing fixtures, documented examples, and earlier configs. If one of those inputs now fails, drop the rejection or name the requirement that states the restriction. Built repeats that check on the implementation. For a field with no earlier input, name that requirement for each of its rejections, or drop the rejection. Test each settled edge, or dismiss it with a reason when no test fits. Record each edge that neither settles as an open gap in the reply, not as a test.
5. **Planned (`principle-separate-before-serializing-shared-state`).** The work is split before anyone builds: gates before fan-out, independent streams named, shared writes separated, the smallest safe decomposition chosen. Write the throughput checkpoint as four items in the same worklist. A dimension that does not apply (single file, no fan-out) still gets its item, marked `skipped: <reason>`:
   - **Blocking first steps.** Gates run before fan-out.
   - **Independent workstreams.** Disjoint files, services, or layers parallelize. Shared writes serialize.
   - **Shared mutable state.** Default to splitting the target. Call the Skill tool with `principle-separate-before-serializing-shared-state`. Serialize only for real invariants. Two workers writing their own field into one file is still shared mutation; give each its own file or key and merge at the read boundary. A lock is a smell to check, not the default.
   - **Smallest safe decomposition.** If one worker is best, name why.
6. **Built.** The step 4 tests pass on the integrated result, and the start commit's tests pass unedited against the new code. First run `python3 "${PSTACK_SKILLS_ROOT:?}/pstack-harness/scripts/preserve.py" --since <start commit>`. For each failure, fix the code or, in automatic mode only, write an allowed reason in a reasons file and then update the test. A required `--command` stays strict; if it needs a waiver, keep Built open and report the unsupported workflow per [preservation modes](../references/delegation.md#preservation-modes). An allowed reason is one block per failure cause: the failing tests it covers, an `input:` line naming what those tests sent, and a `quote:` line holding the spec sentence that forbids that input. The script exits 1 while any failure has neither a fix nor a block, and it cannot judge the sentence, so judge it yourself: a sentence that makes a field required does not cover rejecting the field's values, and a sentence that adds a format does not cover inputs it never mentions. "The schema changed" or "the old tests predate the spec" covers nothing. After assessing every failure and writing the complete reasons file, rerun automatic mode with `--reasons <file>`. If every failure was fixed in code, rerun without `--reasons`. Built stays open until the script exits 0, and the reply carries each block. A start commit of `no commits`, or a run that reports nothing to preserve, satisfies the gate; the step 4 tests still have to pass. Then run each new rejection in the implementation against the inputs the previous version accepted, and drop any rejection whose requirement step 4 did not name. Before implementation, record the planned source file count and independent workstream count in the worklist. Count only the hand-written source files that implement the change. Do not count tests, documentation, dependency manifests, or ignore files. Delegate implementation when the plan changes **three or more source files** or contains **two or more independent workstreams**. Otherwise implement directly and record `implementation delegation below threshold`, the counts, and the reason the work is one workstream. This cutoff is a workflow default, not a measured optimum. If scope crosses the threshold, record the revised counts and delegate the remaining work. Keep the counts tied to the accepted scope, rather than splitting or combining work to avoid delegation. This threshold replaces advisory harness spawn guidance in both directions. Follow higher-priority instructions and actual tool limits. When either prevents a required spawn, own the diff directly with the same review separation and record the specific prohibition or capability limit. Close a delegated unit with the implementation artifact and its reviewed result.
   To delegate, read [delegation](../references/delegation.md). Call the Skill tool with `pstack-harness`, then follow its **Spawn a role** section to resolve the `feature` role. Each brief carries a specific scope: file paths, the step 2 shape and structure, the step 4 tests copied into the delegate's worktree and named as success criteria, and the step 5 workstream it owns. Disjoint file sets get one delegate each, spawned in one message. Coupled work gets one owner whose brief names the split it may make. When the implementation admits multiple valid shapes (error handling, abstraction layer, test structure), call the Skill tool with `arena` to delegate instead, so the runners surface the alternatives and the cross-judge guards the pick. No "standing by" reply that waits on a nested agent. A delegate never writes the only test of its own code. Review every delegate's diff yourself. Parent-level fan-out also covers slices that produce independent artifacts (audits, cross-subsystem investigations, competing experiments). Rewrite the checkpoint at phase boundaries. A phase boundary gets a fresh delegate with consolidated scope, never a resume of the last one.
   Unless the user said not to commit, commit the tests with the code that passes them, so no commit holds tests its code fails. In an existing repository, commit on a branch off trunk, never on trunk itself. Put both instructions in the brief.
7. **Proven (`principle-prove-it-works`).** The integrated result works on the surface the user will use, and every departure from the code around it is named. Call the Skill tool with `principle-prove-it-works`. Check the real thing: run the feature on its surface and read the actual value, not a build status, a file time, or a delegate's report. Rerun on the integrated result, since passing branches do not prove their combination, and prefer a script that reruns the check over one look. Verify against the accepted scope and integrated result. "Inconclusive" or wrong-surface is not a pass. Flag it.
   Brief one read-only reviewer on the `trail reviewer` role with the spec by path and the way to run the integrated result. If you edited the spec, give the version the task gave you instead, such as `git show <commit>:<path>` at the commit the task started from. Leave out your plan, briefs, tests, and your restatement of the goal. It runs the result on inputs it picks from the spec and reports each place where the behavior differs from the spec text. Give the same reviewer the start commit and integrated revision, and ask it to apply [Accumulated complexity](../references/review-lens.md#accumulated-complexity) independently. Keep spec findings and the structural verdict separate. If you cannot spawn the reviewer, report both reviews as not run.
   Then check the integrated diff against the existing code for departures. Behavior-preserving restructuring of the extended unit is not a departure by itself. Report repeated growth without a supported restructure-or-keep decision. Look for:
   - a new component, hook, helper or test helper where one already does the job;
   - a hand-built version of a shared UI piece;
   - a visual choice that differs from nearby screens, such as button variant, row layout, spacing, color or empty/error/loading state;
   - a show/hide or focus behavior that differs from what the replaced or neighboring UI did.

   Search the repository for each. An existing pattern records an earlier taste decision, so overruling one has to be visible. If the design is contested, call the Skill tool with `interrogate` before shipping.
8. **Landed (`principle-sequence-verifiable-units`).** The change sits in small, ordered commits on a branch, each one green on its own. Call the Skill tool with `principle-sequence-verifiable-units`, building, verifying, and committing each small unit before the next. Demonstrate the failing test before the fix during development. Commit the tests with the code that passes them, as step 6 requires. A subtraction lands before the reshape it enables. Rebase into that order. Stack follow-ups. Keep the step 6 branch, per the **Worktree** rule in `playbooks/opening-a-pr.md`. If the project has no git repository, run `git init` in the directory that holds the project's files, and commit on its first branch.
9. **Published.** The branch is where the team reviews changes. Run **Opening a PR**. If the task has no commits to propose, or the repository has no remote, mark this step `skipped: <reason>`.

**Reply:** what you built, what you chose and why, the throughput checkpoint, open decisions, and **Departures from existing patterns**. For each departure, give the pattern it overrules, where that pattern lives, and why the change overrules it, or write None. Carry the same section into the PR body. Tables for design alternatives.
