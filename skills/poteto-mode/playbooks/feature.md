### Feature

**You own the design. Plan, review, verify.** Each step opens with its required outcome. Keep unmet outcomes pending. Only the review handoff in Proven permits publication before that outcome closes. The mode entry's plan script chooses the route before implementation, from the five risk facts in [routes](../references/routes.md). Feature's lightweight route is its compact route. The standard and intensive routes are its full route. Skip a step only as the Playbooks paragraph of the poteto-mode skill allows, and mark it `skipped: <reason>` with a reason that covers that step alone. Where a step says how to run in a new project, run it that way instead of skipping it.

For an ordinary Feature task, open a short worklist before investigation. Keep the playbook path, start commit, current outcome, and pending delivery gates. Assess risk and acceptance first, then build and prove, then deliver with review status. These are tracked outcomes, not copies of all nine steps. Before edits or fan-out, record the five risk facts and rerun the plan script with them. Inspect shared callers, existing checks, and recovery options for those facts.

Use the compact route only when those facts support an understood, low-risk change. Material uncertainty, consequential failures, or contested design require the full route. For work that touches failure or recovery, show where failures are handled, what recovery repeats, and when effects become durable. Compact requires evidence that those boundaries stay intact or that any changes have a settled, low-risk design. Expand the worklist to the full steps before further edits when new evidence changes that decision, including when investigation or verification exposes an unresolved or consequential boundary decision. Retain the opening items and valid completed evidence.

Compact execution combines Preserved, Shaped, and Specified through direct investigation, with the data shape, existing behavior, and acceptance evidence recorded before implementation. It does not require separate `how`, domain-modeling, redesign, architecture, or sequencing skill calls when their outcomes are already established. Keep `spec-probes`, preservation, real-surface proof, and independent scrutiny. Designed is `skipped: one established shape` only when that is true. For serial direct work, record Planned as `skipped: no concurrent writes or independent streams`; omit its four checkpoint items and shared-state skill call. Implement directly without arena or implementation delegation. Record each omitted action and its specific reason in the worklist and reply. Follow Landed and Published within the user's authorization and existing gates.

The steps below define the outcomes for both routes and the procedure for the full route. Explicit operator instructions, decision trails, and machine-consumed playbooks retain their own requirements.

1. **Preserved.** Everything the task does not explicitly change still behaves as it does today, and the step records what that is, with the start commit. Call the Skill tool with `how`, and ask it to list the components, hooks, helpers, and UI patterns the repository already has for this job, and the inputs the program accepts today. Reuse them in the design and in every brief. Extend a shared one only when every caller keeps its behavior. Give the reason for each new one. Reuse covers structure. Another field's rejection does not carry over to a new field; step 4 needs a requirement for each new rejection. The current code's behavior is the spec for everything the task does not explicitly change. Every input an earlier version accepted is part of that behavior. A new rejection needs a requirement you can quote from the spec; without one, accept the input. Call the Skill tool with `principle-redesign-from-first-principles`. Fit the new requirement into the design as if it had been there from day one, with no compatibility branch beside the old path. Apply the review lens's [Accumulated complexity](../references/review-lens.md#accumulated-complexity) check before extending an existing unit. Carry its history evidence and design decision into Proven. In an empty or new project, record `no existing code` as the outcome and keep the step `completed`.
2. **Shaped.** The data shape is named, with the structure that organizes it, before any logic is written. Call the Skill tool with `principle-model-the-domain` to choose that structure. Record in the worklist item the named data shape and its organizing structure, a state machine over scattered booleans, a table/registry over branching, a typed model over repeated shape assumptions, chosen before the delegate writes logic. Every brief in step 6 carries it. Boring code stays when the shape is already clear and local. A feature that grows an if/else chain by one more branch, or adds a second boolean that must stay in sync with the first, is a smell.
3. **Designed.** The shape of the change is chosen, and when the change crosses two or more source files and admits several plausible shapes, the alternatives were compared before any code. Call the Skill tool with `architect` for that comparison on the intensive route. On the standard route, compare the alternatives yourself in a table and raise the route when you cannot choose. A small, self-contained change, or one with a single plausible shape, keeps this step with `skipped: <reason>`.
4. **Specified.** Meaningful acceptance checks cover every new requirement, each traceable to the spec, and every edge the spec leaves open is listed as a gap rather than decided in a test. Reuse existing coverage when it exercises the required behavior and would detect its failure. Add tests for missing behavior coverage before implementation. When the spec gives worked examples or stated formats, cover them with tests, yourself or through a test delegate on the `feature` role whose brief names the source spec by path and adds none of your reading of it. When a spec example first appears, worked or illustrative, copy its input and expected output verbatim, unused fields included, into a fixture file that tests load and later changes never edit. A later change that fails such a fixture reports the conflict in the reply, with both spec sentences, and leaves the fixture alone. Then call the Skill tool with `spec-probes` and follow its edge probe on each new requirement. List the edges its data shape raises from that skill's table, such as boundary values, empty input, ordering, and encoding. Settle each edge from the spec text, or from the current code's behavior when the spec is silent. When the spec defines two similar terms differently, a test fails whichever term is implemented like the other. Each test cites the spec sentence it checks or the current behavior it keeps. Text you add to the spec during the task settles no edge, and no test cites it. A new rejection, error, or reinterpretation of input needs a requirement that states the restriction, even on a new field. Run each new rejection in the tests against the inputs the previous version accepted: existing fixtures, documented examples, and earlier configs. If one of those inputs now fails, drop the rejection or name the requirement that states the restriction. Built repeats that check on the implementation. For a field with no earlier input, name that requirement for each of its rejections, or drop the rejection. Test each settled edge, or dismiss it with a reason when no test fits. Record each edge that neither settles as an open gap in the reply, not as a test.
5. **Planned.** The work is split before anyone builds: gates before fan-out, independent streams named, shared writes separated, the smallest safe decomposition chosen. Write the throughput checkpoint as four items in the same worklist. A dimension that does not apply (single file, no fan-out) still gets its item, marked `skipped: <reason>`:
   - **Blocking first steps.** Gates run before fan-out.
   - **Independent workstreams.** Disjoint files, services, or layers parallelize. Shared writes serialize.
   - **Shared mutable state.** Default to splitting the target. Call the Skill tool with `principle-separate-before-serializing-shared-state`. Serialize only for real invariants. Two workers writing their own field into one file is still shared mutation; give each its own file or key and merge at the read boundary. A lock is a smell to check, not the default.
   - **Smallest safe decomposition.** If one worker is best, name why.
6. **Built.** The step 4 tests pass on the integrated result, and the start commit's tests pass unedited against the new code. First run `python3 "${PSTACK_SKILLS_ROOT:?}/pstack-harness/scripts/preserve.py" --since <start commit>`. For each failure, fix the code or, in automatic mode only, write an allowed reason in a reasons file and then update the test. A required `--command` stays strict; if it needs a waiver, keep Built open and report the unsupported workflow per [preservation modes](../references/delegation.md#preservation-modes). An allowed reason is one block per failure cause: the failing tests it covers, an `input:` line naming what those tests sent, and a `quote:` line holding the spec sentence that forbids that input. The script exits 1 while any failure has neither a fix nor a block, and it cannot judge the sentence, so judge it yourself: a sentence that makes a field required does not cover rejecting the field's values, and a sentence that adds a format does not cover inputs it never mentions. "The schema changed" or "the old tests predate the spec" covers nothing. After assessing every failure and writing the complete reasons file, rerun automatic mode with `--reasons <file>`. If every failure was fixed in code, rerun without `--reasons`. Built stays open until the script exits 0, and the reply carries each block. A start commit of `no commits`, or a run that reports nothing to preserve, satisfies the gate; the step 4 tests still have to pass. Then run each new rejection in the implementation against the inputs the previous version accepted, and drop any rejection whose requirement step 4 did not name. Before implementation, choose direct work or delegation from the accepted scope, dependencies, and useful independent workstreams. The compact route implements directly. On the full route, delegate when separate ownership advances independent work or resolves a named uncertainty. Record the reason for delegation or direct work. Follow higher-priority instructions and actual tool limits. When either prevents a needed spawn, own the diff directly with the same review separation and record the specific prohibition or capability limit. Close a delegated unit with the implementation artifact and its reviewed result.
   To delegate, read [delegation](../references/delegation.md). Call the Skill tool with `pstack-harness`, then follow its **Spawn a role** section to resolve the `feature` role. Each brief carries a specific scope: file paths, the step 2 shape and structure, the step 4 tests copied into the delegate's worktree and named as success criteria, and the step 5 workstream it owns. Disjoint file sets get one delegate each, spawned in one message. Coupled work gets one owner whose brief names the split it may make. When materially different implementation shapes remain unresolved, call the Skill tool with `arena` to delegate instead, so the runners surface the alternatives and the cross-judge guards the pick. No "standing by" reply that waits on a nested agent. A delegate never writes the only test of its own code. Review every delegate's diff yourself. Parent-level fan-out also covers slices that produce independent artifacts (audits, cross-subsystem investigations, competing experiments). Rewrite the checkpoint at phase boundaries. A phase boundary gets a fresh delegate with consolidated scope, never a resume of the last one.
   Unless the user said not to commit, commit the tests with the code that passes them, so no commit holds tests its code fails. In an existing repository, commit on a branch off trunk, never on trunk itself. Put both instructions in the brief.
7. **Proven.** The integrated result works on the surface the user will use, and every departure from the code around it is named. Call the Skill tool with `principle-prove-it-works`. Check the real thing: run the feature on its surface and read the actual value, not a build status, a file time, or a delegate's report. Rerun on the integrated result, since passing branches do not prove their combination, and prefer a script that reruns the check over one look. Verify against the accepted scope and integrated result. "Inconclusive" or wrong-surface is not a pass. Flag it.
   Follow the review lens's [Independent scrutiny](../references/review-lens.md#independent-scrutiny) section. Give its reviewer the spec by path and the way to run the integrated result. If you edited the spec, give the version the task gave you instead, such as `git show <commit>:<path>` at the commit the task started from. The reviewer runs the result on inputs it picks from the spec and reports each place where the behavior differs from the spec text. When human PR review is the chosen scrutiny, follow Landed and Published to deliver an authorized reviewable PR while keeping Proven open.
   After an independent verdict, compare it with the history evidence and design decision recorded in Preserved. Resolve missing evidence or disagreement with the same reviewer before closing Proven.
   Then check the integrated diff against the existing code for departures. Behavior-preserving restructuring of the extended unit is not a departure by itself. Report repeated growth without a supported restructure-or-keep decision. Look for:
   - a new component, hook, helper or test helper where one already does the job;
   - a hand-built version of a shared UI piece;
   - a visual choice that differs from nearby screens, such as button variant, row layout, spacing, color or empty/error/loading state;
   - a show/hide or focus behavior that differs from what the replaced or neighboring UI did.

   Search the repository for each. An existing pattern records an earlier taste decision, so overruling one has to be visible. If the design is contested, call the Skill tool with `interrogate` before shipping.
8. **Landed.** The change sits in small, ordered commits on a branch, each one green on its own. Call the Skill tool with `principle-sequence-verifiable-units`, building, verifying, and committing each small unit before the next. For new behavior coverage, demonstrate a meaningful failure before the fix when the check can expose one. Adequate existing coverage needs no new test or manufactured failing run. Commit the tests with the code that passes them, as step 6 requires. A subtraction lands before the reshape it enables. Rebase into that order. Stack follow-ups. Keep the step 6 branch, per the **Worktree** rule in `playbooks/opening-a-pr.md`. If the project has no git repository, run `git init` in the directory that holds the project's files, and commit on its first branch.
9. **Published.** The reply gives the pull request link, or the branch and how to review it when the endpoint stops short of a pull request. Run **Opening a PR**. If the task has no commits to propose, or the repository has no remote, mark this step `skipped: <reason>`.

**Reply:** what you built, what you chose and why, the route and its evidence, omitted actions and reasons, the throughput checkpoint when used, open decisions, and **Departures from existing patterns**. For each departure, give the pattern it overrules, where that pattern lives, and why the change overrules it, or write None. Carry the same section into the PR body. Tables for design alternatives.
