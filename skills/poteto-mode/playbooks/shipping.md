### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the queue.**

This is the half after `playbooks/babysit.md`.

1. **Resolve the forge, then verify every PR independently.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR view, watch, edit, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One subagent per PR on the `trail reviewer` role, not batched, each a background agent in its own isolated worktree, each exercising the real surface with the matching control skill (the project's `verify-<app>` skill) against parent versus head. In a gated repository, each verifies the head after `checks-passed`. Each returns `PASS`, `PASS+NOTES` or `FAIL` and posts that verdict on its own PR. The verdict comment starts with four lines, each at the start of a line: `Verdict: <PASS|PASS+NOTES|FAIL>`, `Head: <full head SHA>`, `Patch-id: <output of git diff <base>...<head> | git patch-id --stable>`, and `Docs: <pass|needs changes|unverified|n/a>`. When the project has no `verify-<app>` skill, the verifier drives the changed surface by hand (the CLI, server, or page the change touches) and names what it drove. A verifier that ran only tests returns at most `PASS+NOTES` and names the surface it did not drive. That PR stays landable, and the reply reports the undriven surface. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.

   Require the author's **documentation-impact** result, with its evidence and examined artifact, in each PR record. When it is `independent review required`, spawn the reviewer on the `trail reviewer` role and assign `review` mode in its initial brief and record the independent review verdict, identity, and examined artifact. The reviewer can reuse a current independent review verdict. Return repairs to the author, then review the resulting artifact. When it is `independent review not required`, do not start an independent review.

2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing code verdict, an author result, or a current independent review verdict of `pass` when that result requires independent review. For code, both `PASS` and `PASS+NOTES` pass. Missing evidence or unresolved documentation findings stop the verified run. A verified PR sitting above an unverified one is not landable. Report the ceiling as a PR number and say what breaks the chain.

3. **Re-check that each verdict still describes the patch.** Record the verdict head SHA, base SHA, and stable `git patch-id` of that PR's base-to-head diff. A rebase or base retarget rewrites SHAs and can silently invalidate a verdict without touching a check. Before landing a PR, compare the recorded patch-id with its current base-to-head patch-id. When the two patches differ only in tests, docs, or lint config, build what each lane ran. Build it twice at the verdict SHA and once at the current head. A difference is noise if the two builds at the verdict SHA also show it, or if it is an embedded commit SHA. Judge each difference, not each file, and report each kind of noise with its files. If only noise differs, that lane's result stays valid, and checks and a review of the change run fresh. Do not reuse a lane result from a dev server or from anything else with no build output. Rerun that lane. Re-verify anything else when the patch changed. When it did not, keep the code verdict but re-run mergeability and CI at the current head. Never use matching commit messages or a green check from an older SHA as a substitute.

   Recheck the author result using **documentation-impact**. Even when the patch-id matches, changed base documentation or surrounding behavior can invalidate the result. Confirm that context still matches or rerun the author pass before landing. When the author result requires independent review, also confirm that the independent review verdict remains current or rerun the independent review.

4. **Prepare only the bottom PR.** In a gated repository, follow the gated publish rules in `playbooks/opening-a-pr.md`. Leave a conflict to the live CI monitor. Replace this step's rebase, push, and retarget with `no-mistakes rerun --base-branch <trunk>` only after a terminal outcome or once the monitor has stopped. When a retarget is needed while the monitor is live, report it and do not act. Fetch current trunk. Rebase the lowest verified branch onto the exact trunk tip when needed, push it, and retarget only that PR to trunk with `origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`. Re-run step 3 after the push. Do not retarget, arm, or merge descendants yet.
5. **Land one PR at a time.** If the bottom PR is mergeable now, land it. On GitHub, run `scripts/watch-pr/merge-gate --pr <pr> --subject <subject> --body-file <body>`. It merges only when every gate holds. The latest trusted verdict block must match the current patch-id. Every check must pass. Every bot's latest review body must be acknowledged. No thread may be open, and the PR must be mergeable. When a gate fails, it names every failed gate, exits 10, and does not merge. Fix or report each failed gate. A base branch with a merge queue fails the `merge-queue` gate the same way, because `gh pr merge` would only enqueue the PR, and the queue would land it later without rechecking the verdict, the bot reviews, or the open threads. Pass `--override "<reason>"` only when the user approves landing over a failed gate. The override posts the reason on the PR. On Origin, check the same gates by hand, then squash with `origin pr merge <pr> --squash`. If requirements are still running and the user asked for merge-when-ready, on Origin arm only that PR with `origin pr merge <pr> --squash --auto`, which is Origin merge-when-ready. On GitHub, never arm GitHub auto-merge, because it merges later without merge-gate's verdict, patch-id, and review-body checks. Run the watcher instead, and run merge-gate when the watcher reports `READY` at the PR's current head. When merge-gate exits 11, the merge is queued or not yet confirmed. Watch it per step 8. Wait for that PR to merge before preparing the next one. Send a `review-findings` blocker (exit 8) back to Babysit step 8.
6. **Do not read GitHub `autoMergeRequest` as stack readiness.** At most it says GitHub auto-merge was requested for one GitHub PR. It does not prove Origin merge-when-ready is armed, that a descendant is queued, that a patch verdict is current, or that the contiguous stack is safe. Confirm the active forge's state for the current bottom PR, and say that the state is unknown if the active forge cannot report it.
7. **Recompute after every merge.** Fetch trunk, confirm the merged SHA is present, drop the merged PR from the frozen bottom-to-top list, delete its `refs/pstack/wip/<branch>` snapshot ref if one exists, and inspect the new bottom PR's base, head, checks, and patch-id. A host may retarget a child automatically, but do not assume it did. Repeat steps 3 through 6 for that one PR. Independent work stays outside this chain and ships on its own.
8. **Watch the current frontier until it merges or fails. Do not mutate the queue around it.** With Origin, use `origin pr view <pr> --checks --comments` and `origin pr checks <pr> --watch`, then re-read the PR until it reports merged or blocked. With GitHub, after merge-gate exits 11, use `scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom>` only as an event wake and poll `gh pr view <pr> --json state,mergedAt,mergeStateStatus,statusCheckRollup,autoMergeRequest` after each wake, ignoring `READY` until `mergedAt` is non-null or `state` is `MERGED`. Only then run step 7. Hard-fail only when `state` is `CLOSED` with no `mergedAt`, a required check concludes `FAILURE` or `CANCELLED` and blocks merge after auto-merge is no longer pending, or `mergeStateStatus` is `UNSTABLE` or `DIRTY` with no auto-merge pending. `BLOCKED` while checks are pending or auto-merge is armed is not failure. A `review-threads` or `review-findings` blocker from the wake goes back to Babysit step 8 before the queue moves. Do not use Babysit's queued `WAITING`/`merge-queue` stop condition here. Hold the watch under `/loop` in dynamic mode. Report each merge and the new ceiling. If the queue stalls, diagnose before mutating.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's code verdict, author result, and required independent review verdict, who produced them, and the examined artifact, what you armed and how you confirmed it, what landed, and what the next gap needs.
