### Refactoring

**You own the contract. The structure changes. The behavior does not.** Each step opens with the outcome that must hold before the next step starts. The mode entry's plan script chooses the route from the five risk facts in [routes](../references/routes.md). On the lightweight route, make the edits yourself and load only the skills the plan lists. Distinct from Feature, which adds behavior, and Bug fix, which corrects it. If the cleanup reveals a missing feature or a real bug, split it out and ship the structural change first against the pinned contract. A redesign is allowed, but name it and route to Feature. For large or cross-cutting structural work, call the Skill tool with `figure-it-out`. This playbook is the focused-to-medium change.

1. **Pinned (`how`).** A test, snapshot, or equivalence harness captures the current behavior, is committed as a file later steps never edit, and runs green before any structure moves. Record that commit as the start commit. Pin the behavior contract first. Call the Skill tool with `how` on the affected subsystem to learn the contract. Reuse existing tests as the pin when they exercise that contract and would fail if it broke. Name them, and record the commit that holds them. Otherwise write a characterization test, snapshot, or equivalence harness that captures current behavior. If the area has no coverage, write the pin before touching structure. Type check and lint are not a pin.
2. **Shaped (`principle-model-the-domain`).** The structure the code is missing is named, and the reshape deletes branches or invalid states rather than adding indirection. Call the Skill tool with `principle-model-the-domain`.
3. **Targeted (`principle-foundational-thinking`, `principle-redesign-from-first-principles`).** The module layout, types, and call graph the code should have if built today are written down. Call the Skill tool with `principle-foundational-thinking`. Call the Skill tool with `principle-redesign-from-first-principles`. If the target crosses two or more source files and admits several plausible shapes, call the Skill tool with `architect` for parallel design exploration of the shape before the move on the intensive route. On the standard route, compare the shapes yourself in a table.
4. **Subtracted (`principle-subtract-before-you-add`).** Dead code, one-caller wrappers, redundant validators, and orphan references are gone, with the pin still green, before the new shape arrives. Call the Skill tool with `principle-subtract-before-you-add`. Ship the simplest adequate design that reaches the target shape. Call the Skill tool with `principle-laziness-protocol`. A speculative cleanup that "might help" gets reverted.
5. **Moved (`principle-migrate-callers-then-delete-legacy-apis`).** The new shape is in place through small steps, each keeping the pin green, with every caller migrated and the old API gone. For API reshapes, migrate every caller and delete the old API in the same wave. Call the Skill tool with `principle-migrate-callers-then-delete-legacy-apis`. No compatibility shims, no parallel old-and-new paths. Spot-check every rename against the actual files. Renames silently miss usages in strings, prose, and back-references. If the repo has a GitNexus index (`.gitnexus/` exists) and `gitnexus` is on `PATH`, refresh it first (`gitnexus analyze --index-only`, incremental and a no-op when up to date; rerun it whenever a staleness notice appears mid-wave before the next graph query), then enumerate callers with `gitnexus impact <symbol>` and `gitnexus context <symbol>` before the wave, and still spot-check against the actual files, because the index reflects the last analyzed commit and never sees uncommitted edits. Off the lightweight route, delegate the mechanical edits to a subagent on the `refactoring` role with a specific scope (file paths, the names being moved, the behavior to hold). Call the Skill tool with `pstack-harness`, then follow its **Spawn a role** section to resolve the role.
6. **Proven (`principle-prove-it-works`).** The real artifact behaves as the pin says, not "it compiles", and the start commit's tests pass unedited against the new structure. Run `python3 "${PSTACK_SKILLS_ROOT:?}/pstack-harness/scripts/preserve.py" --since <start commit>`. No failure is allowed here: a failing earlier test means the behavior changed, so revert the move or route the change to Feature. Call the Skill tool with `principle-prove-it-works`. Check the real thing: run the artifact and read the actual value, not a build status or a delegate's report, and rerun on the integrated result. For larger reshapes, run an equivalence check: a script that diffs old-vs-new outputs, a recorded baseline replayed against the new code, or a smoke run on the matching surface via the relevant control skill. Then follow the review lens's [Independent scrutiny](../references/review-lens.md#independent-scrutiny) section, and give its reviewer the pin.
7. **Worth it (`principle-minimize-reader-load`).** The diff lowers reader load somewhere, or it is reverted. Call the Skill tool with `principle-minimize-reader-load`.
8. **Landed (`principle-sequence-verifiable-units`).** The change sits in small ordered commits, a subtraction commit, then the reshape, then any follow-on cleanup, each green on its own. Call the Skill tool with `principle-sequence-verifiable-units` to shape them: each unit ends in a check that runs before the next unit starts, and the order reads as an argument a reviewer can replay. Run **Opening a PR**.

**Reply:** the structure that changed, the pin you held it against, the equivalence proof, the reader-load delta, what shipped and what got reverted. No new behavior.
