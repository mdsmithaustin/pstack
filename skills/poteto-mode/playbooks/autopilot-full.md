### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean verifier verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits. A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The patch-id rule in `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. The grant covers only the queue's items, so PRs outside the queue also stop at merge-ready. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Use the **pstack-harness** skill to resolve the portable roots. Keep their concrete values in private, untracked run state and pass them to every owner. Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One background agent per PR (its own isolated worktree) owns build, the first push, a ready PR, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical Bugbot triage per `../references/bugbot-triage.md`, a slop-strip with the **deslop** skill, a comment review with the **no-comments** skill, a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself. Within about 15 minutes, every owner uses the **show-me-your-work** skill to start a `decisions.tsv` trail, pushes its first branch snapshot, and opens the PR ready, never draft. In a gated repository, follow the gated publish rules in `playbooks/opening-a-pr.md`. Snapshots go to the snapshot ref, the PR opens through `no-mistakes axi run`, and each rebase follows the `rerun` rule there. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. If the owner dies, the root can still probe each child. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. Verification then runs on the base the patch lands on. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. Each rebase restarts CI. When the shipped code is final, after the slop-strip and the comment review, it reports the code-ready head SHA. The full swarm then runs on finished code. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with the swarm. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks that the repo's AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. In an ungated repository, publish each rebase by pushing the owner's own branch with `git push --force-with-lease` after an `ls-remote` check, with the lease pinned to the SHA the owner last pushed or took over. On any push the owner did not make, it stops and reports to the root. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. Either way, each PR lands on its own. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Verify every round before its merge.** A round starts at the owner's code-ready head SHA and at each later push that changes the PR's patch. A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head, and its verdict counts as that round's verdict. A single verifier is one independent verifier. It re-runs the gates, re-runs the live lane on every surface the patch changed since the last full swarm, and re-checks each finding the last `FAIL` sent back against the focus of the lane that raised it. When it finds new behavior, a redesign, or a large new diff, the round becomes a full swarm. Plan required live proof before the operation it observes. For each observation, name the already-authorized actor, the earliest existing checkpoint where it is observable, and the actual source to inspect. Keep evidence that is not yet observable pending in the existing report or decision trail. Missing or unknown evidence, or an observation with no currently authorized actor, remains a proof gap. Report owner observations separately from the no-mistakes Test step's own scenarios, when the repository is gated, and name each actual source. If that Test step ran no live scenarios, report zero; in an ungated repository, report that the Test step did not run. Historical reads and green CI status alone do not establish current consumer behavior. A later observation does not supply proof to an earlier verdict. For a full swarm, use the **swarm** skill at the round's head SHA to fan out parallel independent verifiers, and aggregate to one verdict. The merge needs a clean verdict from the round whose patch matches the merge-ready head. Post that verdict on the PR in the four-line block of `playbooks/shipping.md` step 1, so the owner's merge-gate run can read it. Audit the receipts in the merge-ready report before the verdict. Neither you nor a lane trusts a claim without checking it. A full swarm's lanes: re-run the gates at that SHA. Prove the load-bearing behavior live on the real surface the change touches (through the project's `verify-<app>` skill, or a named driver where none exists). Audit the diff, distrusting the PR body. Run the audit as two or more review lanes with the full brief. Give each lane one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. When the lanes return, send the owner one fix-forward with every proven finding that falls inside the PR's scope, meaning the issue or request the PR serves, and that a real caller, a real input, or a recorded run reaches. A recorded run is a saved run of a real caller or a real input, with a transcript or artifacts the verdict can cite. A lane's run on an input it invented is not a recorded run. For a docs, prompt, or config change, the agent or tool that reads it is the caller. A note that meets this bar is a finding. A defect trunk shows without the PR is recorded against trunk and does not gate the PR, but one the PR copies or newly reaches is the PR's own. Never push a fix yourself, because each branch has one writer. Replace a stuck owner instead. File every other true finding as a follow-up issue linked from the verdict, including one that only an input the lane invented reaches. Security, privacy, auth, data, and permission-boundary findings are the exception. Never file one as a public issue, and never post or link one on the PR. Send a proven one inside the PR's scope that a real caller, a real input, or a recorded run reaches to the owner in the fix-forward. Ask the operator directly about every other one, including an in-scope one that only an invented input reaches, per **Ask by default** in `../references/bugbot-triage.md`. A round whose remaining findings all went to follow-up issues is clean and posts `PASS+NOTES`. A round that sends findings back posts `FAIL`. A round with a security ask open also posts `FAIL`, because the PR is not merge-ready until the operator answers. When that round sends nothing back, add the line `Operator ask: open` after its block, so its `FAIL` does not count toward the stop. When the round also sends findings back, omit that line and count its `FAIL`, even while the ask remains open. Post the round's `FAIL` first, then read the stop state before the fix-forward. Run `../scripts/watch-pr/merge-gate --pr <pr> --check`. Exit 10 means a gate failed, which is not an error here. Exit 1 means the count is unknown, for example after a failed `git fetch`. Hold the fix-forward and run `--check` once more. If it exits 1 again, report the unknown count to the operator and keep holding. Before you act, confirm that `report.verdict` is `recorded` at this round's `Head`. If it is `malformed`, post the corrected block as a new comment and run `--check` again. Never edit a posted block, because an edit keeps the comment's original time. Then read `report.failRounds`. `count` is the number of distinct rounds among trusted `Verdict:` claims whose word is not `PASS` or `PASS+NOTES` and that lack that line, and it includes this round. A malformed claim counts. A claim's round is its `Head` when that line parses, and the claim itself otherwise. A reset never clears this total. With `--pretty`, the headline shows `fail-rounds` and `fail-state`, with `+` after the count when the comment history is incomplete. `../scripts/watch-pr/verdict.ts` reads `Verdict:` claims, `Fail-count reset:` comments, and `Stopped:` comments only from trusted commenters, by the same rule as verdict blocks. When `report.failRounds.complete` is false, the PR has more comments than the read holds, so read all of them and apply these rules by hand. When `state` is `open`, send the fix-forward. When it is `stop`, meaning the third counted `FAIL` or the first after a reset, send nothing. Stop the owner and report the PR to the operator with what blocks it. File each open finding as a follow-up issue once, except security findings, which stay with the operator. Post one PR comment that starts with `Stopped:` and links the issues. When it is `stopped`, file nothing and report the PR as blocked again. An operator's go-ahead grants exactly one more round. The root posts a PR comment whose first line is `Fail-count reset: <reason>` and that summarizes the go-ahead. Neither the reason nor the summary names a security finding. That reset supersedes the `Stopped:` comment, and the next counted `FAIL` stops again. For events in the same second, apply the reset first, then `Stopped:`, then `FAIL`, so a tie never hides a stop. The root then sends the owner the open findings as one fix-forward. For each behavior finding, ask for a red test that covers every site with the same defect. Where no test can show the defect, ask for a repro receipt instead. Add that defect to the next round's review brief. The new head gets a fresh verdict, from a full swarm or a single verifier per the rule at the start of this step, except for lane results that stay valid under the patch-id rule in `playbooks/shipping.md`.
5. **On a clean verdict the owner merges, and a fresh owner takes the next item.** The owner merges only from a head freshly rebased onto trunk. In a gated repository, perform merge preparation through **Gated merge preparation** in `playbooks/opening-a-pr.md`. Merge prep never comes before a round's lanes start, and it ends with a rebase onto current trunk right before the merge. After the merge-prep rebase, the owner reports the new head SHA. CI must pass on that head before the merge, and the patch-id rule decides whether the round's verdict still holds. Once that head is green and its patch-id matches the verdict's under the patch-id rule in `playbooks/shipping.md`, a later trunk move does not force another rebase. Rebasing for every trunk move never ends. Right before the merge, fetch trunk and check that `git merge-tree` of the head against current trunk is clean. Also check that no path in `git diff --name-only $(git merge-base HEAD origin/main) origin/main` is a path the PR changes or a path that decides which CI runs for it, such as the repo's CI config paths. If either check fails, rebase again, report the new head SHA, wait for CI to pass on it, and repeat these checks. Either failure means CI never tested the code that would land. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land. A failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge only on a pass. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work. A new head voids the verdict unless the patch-id is unchanged. The owner squash-merges its own PR through the resolved forge, with `../scripts/watch-pr/merge-gate` on GitHub per `playbooks/shipping.md` step 5, and returns. A fresh owner picks up the next self-contained item from the queue, per poteto-mode's [delegation reference](../references/delegation.md). The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. The grant never approves `--override` for any refused gate. When `merge-gate` refuses because the base branch has a merge queue, the owner stops at merge-ready and the root reports an open operator gate. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. No countersign covers a forge-enforced approval. Absorbing values that already landed on main is drift, not a raise. Anything else that loosens a gate, such as an allowlist entry, needs the same proof and countersign, because the owner is the one who wants green. A disabled or soft-failed check always comes out, because it stops guarding every case. Run an audit tick over all owners every hour. Long runs drift, and agents can stall without reporting it. On the operator's go, use the **pstack-harness** skill's [loop procedure](../../pstack-harness/references/loops.md) to arm the tick through the harness's loop facility, with a prompt that runs this tick. In Claude Code that is `/loop 1h`. Never leave the cadence to memory or lossy completion notifications. Restore the recorded roots at each tick. Re-read this playbook from trunk with `git -C "${PSTACK_SOURCE_ROOT:?}" fetch origin '+refs/heads/main:refs/remotes/origin/main' && git -C "$PSTACK_SOURCE_ROOT" show 'origin/main:skills/poteto-mode/playbooks/autopilot-full.md'` and audit the operation against it. Fix drift during that tick. If that fetch fails, skip the drift fix for this tick, run the rest of the tick, and record the failed fetch in the trail. Never skip the tick because the fetch failed. Probe each owner with a generic liveness or status check, and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Status text and summaries can hide a stuck child. Side effects do not show convergence, so each tick also reads `report.failRounds` for every PR and acts on its `state` per step 4. Treat a lane that errors, or that passes its expected runtime without a side effect, as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. The tick judges an owner by the pushed branch and the decision trail that step 2 requires, and it replaces an owner whose agent cannot start a turn or that has neither pushed nor written a trail row by the first tick. An agent waiting on you or the operator is not stuck, so answer it. Each tick also runs the lane stuck test over the program's agent list, where the platform has one, and over every owner's `children.tsv`. Whether or not a stop works, the root has the owner record each stuck subagent as stuck and, if its work is still needed, replace it. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. End the tick only when no delegated work is left, even after the last merge. A tick that changed something for the operator ends by catching them up. Use the **ketchup** skill. A tick that changed nothing stays quiet.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Each owner reports where it stands and holds its brief until the operator releases it.

**Reply:** Use the **ketchup** skill. Catch the operator up on the queue with each PR's owner, state, and head SHA. Each verdict and the swarm or verifier that produced it. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Link each PR and where the collected decision trails live.
