### Opening a PR

Invoked at the end of every other playbook. Short of a pull request, stop at the endpoint: always commit, push only for a pushed branch, and name the branch in the reply.

Read this playbook in full. It has no numbered steps.

Work from a git worktree off trunk, and keep unrelated work out of it. If `git worktree add` fails and the checkout holds no unrelated changes, branch off trunk there. Otherwise, or if that fails, stop and report. Never commit to trunk. Rebase into small, landable commits. Before each push or published head, call the Skill tool with `deslop`. On the intensive route, in a machine-consumed playbook, or when a brief says so, do it before every commit or amend instead. Complete its [Before each commit](../../deslop/SKILL.md#before-each-commit) check over that scope's commits and keep the evidence.

**Titles.** `type(scope): subject`, naming a real symbol when one carries the change.

**Body format.** The user's explicit format wins, then the repository's PR template or documented format. Another PR-writing skill's layout never replaces this choice. Otherwise the body is a one-minute briefing under 40 lines with these `##` headings in order: `## Why`, `## What changed`, `## Scope`, `## Tradeoffs` (only rejected alternatives a reviewer would otherwise ask about), `## Blast Radius`, `## Verification`. Drop only an empty Tradeoffs, and state a known gap instead of inventing content. Feature PRs add `## Departures from existing patterns` after Scope, or after a repository template's own sections. Keep no-mistakes pipeline and testing evidence beside the author sections. Attach videos or screenshots that prove a claim, following any attachment rule in the repository's `AGENTS.md` or PR template. After the PR opens, post the swarm report or arena synthesis note as a PR comment, leaving out any finding that `playbooks/shipping.md` step 1 keeps off the PR, and link it from `## Verification`. Before publishing, run `python3 "${PSTACK_SKILLS_ROOT:?}/poteto-mode/scripts/check-writing.py" title "<title>"` and the same script with `body <file>`, adding `--no-headings` when the user or a template sets the format, and fix each failure.

Finalize the body last. Before you report merge-ready, check each Scope and Blast Radius claim, and each quantifier such as "all" or "preserved", against the PR's full diff at the current head, and publish a rewrite of any stale claim. Check a review-thread reply the same way before posting it.

Stack follow-ups by base branch. Open PRs ready, through the run's PR tool with `draft: false`. Without one, use `gh pr create` without `--draft`, or `origin pr create --status open` when `command -v origin` succeeds and Origin's CLI resolves the repository. Keep that forge for every later PR operation. For `gh`, resolve `<host>/<owner>/<repo>` from origin's fetch URL, never `gh`'s default repo, which in a fork can be the parent. Pass it as `-R` to every `gh pr` and `gh issue` call, reads included. `gh api` takes it in the endpoint path, and `gh api` and `gh auth token` take `--hostname <host>`. In an ungated repository where neither the PR tool nor a CLI can open the PR, push the branch, report that no PR exists, and name the branch. For upstream-sync publication and its draft rule, follow [Syncing from upstream](../../../PORTING.md#syncing-from-upstream).

**Gated publish.** A repository is gated when `NO_MISTAKES_GATE` is set, when your brief says so, when it commits `.no-mistakes.yaml`, or when `git remote get-url no-mistakes` succeeds. `SANDBOX_NAME` alone does not make it gated. Then read [gated publish](../references/gated-publish.md) in full before the first commit, amend, push, PR operation, rebase, or merge preparation. Its rules override every push, rebase, PR creation, PR tool call, stack, and retarget here and in other playbooks. In an ungated repository, do not read it.

**Attachments.** Upload through the forge CLI, never a browser you drive. Use Origin's attach flag when `origin pr create --help` lists one, else `gh` for a GitHub repository. Pass `--attach '<path>#<alt text>'` to `gh pr create`, `gh pr edit`, or `gh pr comment` once per file. It rewrites a body reference to that local path, and needs gh 2.99.0 or later and push access. Never use undocumented endpoints. A CLI rejection, as on some Enterprise hosts, is a CLI limit, not a repository ban. Do not retry it. Ask for a web upload and the pasted URL only when the user authorized one, else report the upload unavailable. For `https://<host>/user-attachments/assets/` URLs, read the PR back with `gh pr view <number> -R <host>/<owner>/<repo> --json body,comments` and fetch each URL with `curl -s -o /dev/null -w '%{http_code}' -L -H "Authorization: Bearer $(gh auth token --hostname <host>)" <url>`. It must return `200`, and a signed-out fetch proves nothing. If a CLI upload's URL fails, attach once more. Report upload availability, the saved PR content, and the fetch result separately, with the gh version and any error. Recap sketches follow [pr-recap's posting checks](../../pr-recap/SKILL.md#post-or-update-the-comment).

**Recap.** Only when the user or the repository's contributor instructions ask for one, call the Skill tool with `pr-recap` after the PR opens. Refresh it per [task triggers](../references/task-triggers.md).

Opening a PR does not start a babysit. A non-owner subagent that opens a PR finalizes the body, posts the URL, and returns without babysitting. An Autopilot-full or Autopilot-stack owner runs the babysit loop its brief assigns after its code-ready report, then reports merge-ready or STACK-READY per its playbook.
