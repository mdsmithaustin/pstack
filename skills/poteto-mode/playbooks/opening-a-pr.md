### Opening a PR

Use when the matched playbook produces a PR.

Read this playbook in full. It has no numbered steps.

**Worktree.** Work from a git worktree off main. Subagents inherit it. If `git worktree add` fails and the current checkout holds no unrelated changes, create the branch off main in that checkout. Otherwise, or if that also fails, stop and report the failure. Never commit to main. Multiple `Task` calls on the same branch each get their own worktree, or `git fetch && git reset --hard origin/<branch>` between them. Dirty branch with unrelated work: patch out, fresh worktree, apply. Snarled worktree: reset from main, redo minimally.

**Commits.** Commit liberally. Rebase into small, ordered commits before opening PRs. Each commit is a future PR: landable, ordered to tell the story. Amend when the fix belongs in a just-made commit. New commit when separable. Commit bodies don't restate the subject.

**PRs.** Before every commit or amend, use the **deslop** skill. Complete its [Before each commit](../../deslop/SKILL.md#before-each-commit) check and retain the per-commit evidence. Use the **no-comments** skill before review. Use the **technical-writing** skill for every PR title, PR description, and commit body. Then use the **unslop** skill. Apply every technical-writing layer except Diátaxis, and apply the STE vocabulary rules: use one word for each action, keep articles, and use a plain verb over `-ing` where one works.

**Titles.** Conventional Commits `type(scope): subject`, no trailing period. Type such as `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, or `perf`. Scope is the area, such as `pstack` or `poteto-mode`. Subject is short, imperative, and names a real symbol when one carries the change, for example `fix(pstack): retarget opening-a-pr babysit trigger`.

**Descriptions.** The PR body is a one-minute briefing, not a lab notebook, for a reviewer who has the diff. It says why the change exists, what it leaves out, what it could break, and how you proved it works. Write short, simple sentences with few identifiers, no walls of text. The body becomes the squash commit body, so keep that commit under about 40 lines. A body written when the PR opens early is provisional. Finalize the body last, from the PR's full diff at the current head, before you report merge-ready. Check each claim in `## Scope` and `## Blast Radius`, and each quantifier such as "all", "most", or "preserved", against that diff. Rewrite stale claims and publish the corrected body through the resolved forge or the built-in PR tool per the rules below. Hold a review-thread reply to the same check before posting it.

**Body format.** Follow the user's explicit format, then the repository's selected PR template or documented format. Otherwise use the poteto defaults below. Other PR-writing skills, when installed, can guide prose but their default layouts do not replace this selection. Keep no-mistakes pipeline and testing evidence in addition to the selected author sections.

For the poteto defaults, use `##` headings in this order. Keep Why, What changed, Scope, Blast Radius, and Verification. State a known gap or that verification was not run instead of inventing content:

- `## Why`: the problem and approach, 1–3 short sentences. No SHAs, rebase genealogy, or "based on main" preamble.
- `## What changed`: 1–3 short bullets. Name a real symbol or path only when it carries the change. Name both sides of a rename or retarget.
- `## Scope`: always. 1–3 short items on what it covers and what it deliberately leaves out (a follow-up, a known gap). No symbols, paths, or file-by-file essay.
- `## Tradeoffs`: only rejected alternatives a reviewer would otherwise ask about. Skip when there was no real choice.
- `## Blast Radius`: 1–2 sentences on who or what it touches and why that is safe or risky. If main is red, state the cost of leaving it red.
- `## Verification`: 1–3 bullets, each a real run path and its outcome. Perf: one primary number with its unit, `before → after`, and a link to the rest. After the PR opens, post the swarm report or the arena synthesis note as a PR comment, leaving out any finding that `playbooks/shipping.md` step 1 keeps off the PR, and link that comment when you finalize the body. No sample-size methodology, swarm recitals, or metric tables.

After the sections, attach videos or screenshots when they prove a claim, and follow any attachment rule the repo's `AGENTS.md` or PR template sets, such as a Demo section. Full SHAs, swarm or arena lane recitals, lever-correction essays, file-by-file checklists, and "CLEAN" verdicts go in a linked artifact, not the body.

**Forge.** Resolve the forge before the first PR operation and keep that choice for create, edit, view, watch, and merge. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, prefer `origin pr ...`. If Origin is absent or cannot resolve the repository, stay on `gh` and record the fallback. Do not require Graphite (`gt`). Resolve the repository as `<host>/<owner>/<repo>` from origin's effective fetch URL at the same time, for both github.com and GitHub Enterprise. Never rely on `gh`'s default repo. In a fork with an `upstream` remote, `gh` can resolve it to the parent, and a bare `gh pr create` or `gh pr view` then acts on the wrong repository. Pass the full `<host>/<owner>/<repo>` repository as `-R` to every `gh pr` and `gh issue` call, reads included. With `-R`, pass the PR number or URL to commands on one PR. `gh pr view` also accepts the branch name. `gh api` rejects `-R`, so put the repository in the endpoint path (`repos/<owner>/<repo>/...`). `gh auth token` takes no repository. Pass `--hostname <host>` to both, including when the host is github.com. In an ungated repository, when the run has no built-in PR tool and neither CLI can open the PR, push the branch, report that no PR exists, and name the branch.

**Gated publish.** Resolve the publish path with the forge, before the first push.

- When `NO_MISTAKES_GATE` is set, you are a no-mistakes pipeline step. Never push, open a PR, or start a run.
- When `SANDBOX_NAME` is set, you run in a sandbox clone, which has no `no-mistakes` remote. When your brief says the repository is gated, or the repository commits `.no-mistakes.yaml`, commit on a feature branch and never push. Report the branch, the head SHA, and that a gated publish is needed. The host fetches the branch from its `sandbox-<name>` remote and publishes it.
- Otherwise the repository is gated when `git remote get-url no-mistakes` succeeds and `no-mistakes axi` prints no `error:`. When the remote exists but `no-mistakes axi` prints `repo not initialized`, stop and report it. On a case-insensitive disk, the likely cause is that `init` ran from a path spelled differently from the main checkout's path, the parent of the directory that `git rev-parse --path-format=absolute --git-common-dir` prints. The fix is to re-run `no-mistakes init` from that exact path. When the remote exists and `no-mistakes axi` prints any other `error:`, the gate is broken. Stop and report the error. When the repository commits `.no-mistakes.yaml` but has no `no-mistakes` remote, stop and report that `no-mistakes init` must run from the main checkout's path, the parent of the directory that `git rev-parse --path-format=absolute --git-common-dir` prints.
- When you launch a sandboxed agent on a gated repository, say in its brief that the repository is gated.

In a gated repository, the gate owns every write to the push target and every PR it opens. These rules override every push, rebase, PR creation, and retarget in other playbooks, which apply only to ungated repositories. When the no-mistakes skill is installed, read it and follow its run, gate, and `branch_sync` rules. Otherwise use `no-mistakes axi --help`.

- Never run `git push` or `git push --force-with-lease` to the push target. Publish a branch and open its PR with `no-mistakes axi run --intent-file <file> --no-publish-intent`. Write the user's goal and decisions into the intent file. For a stacked child, add `--base-branch <parent-branch>`. To reattach after a wait, run `no-mistakes axi run` with no intent.
- Never create or retarget the PR with a forge CLI or a built-in PR tool.
- Never rebase a published branch by hand. Leave conflicts to the live CI monitor. After a terminal outcome, or once the monitor has stopped, restack or retarget with `no-mistakes rerun --base-branch <new-base>`. For merge preparation with a residual monitor, follow **Gated merge preparation** below.
- Push work-in-progress snapshots only to `refs/pstack/wip/<branch>` on origin. When the repository's AGENTS.md, CLAUDE.md, or CONTRIBUTING names a branch or ref convention for agent work, use that convention. When the remote rejects the ref, keep snapshots local and record why. Do not retry under another name. Delete the snapshot ref after the PR merges, following **Snapshot cleanup** below.
- Before any local commit or `rerun` on a published branch, read `branch_sync` and follow its `next_action`. Commit only when it allows a commit.
- Relay an `ask-user` finding verbatim to the user, or from a subagent to its parent. Pass `--yes` only when the user's grant names no-mistakes.
- When `no-mistakes doctor` fails or the gate cannot run, stop and report. Publish around the gate only when the user said "bypass no-mistakes" in this session.
- Before the first run, check whether the repository config selects `pr.template`. A template file alone does not select no-mistakes template mode. For setup, use the **setup-pstack** skill's [PR template instructions](../../setup-pstack/references/pr-template.md). The template path and bytes must already be on the trusted default branch to affect the run. When setup is pending, retain the selected body format for post-run finalization.
- After each run that creates or updates a PR, read its live body. Check the title against **Titles**, restore the selected **Body format**, and check every author claim against the PR's full diff at the current head. Correct the title and author text with the resolved forge. Preserve the generated evidence appendix, ownership markers, and attestation byte for byte; put author additions outside it. Read the PR back and verify the selected sections and unchanged generated evidence before reporting merge-ready. A later generic run can overwrite author sections again, so repeat this check after every publication until template mode is active. The squash body comes from `merge-gate --body-file` in `playbooks/shipping.md`.
- `axi run` and `axi respond` block for up to 8 minutes. Give each call a tool timeout of 10 minutes. After `rerun` starts a new run, drive that run with `no-mistakes axi run` (reattach) and `axi respond` until it reaches an outcome.

**Snapshot cleanup.** Use only the already owned snapshot ref for the merged PR. Read it with `git ls-remote --refs <remote> <full-owned-ref>`. Check the exit status and match the returned full ref exactly. A successful read with no match means cleanup is done. A failed read, unknown ownership, unexpected ref, or changed object holds cleanup. `<expected-oid>` is the commit this owner last successfully pushed to the exact owned snapshot ref, established from that successful push operation or its existing evidence. Compare the freshly read object to that independently known commit. A fresh remote read or ref name alone establishes no ownership. If this owner cannot establish its own successful push and object, hold cleanup. Validate every target before the batch's first deletion. For a matching target, use `git push --force-with-lease=<full-owned-ref>:<expected-oid> <remote> :<full-owned-ref>`. Inspect each result before dependent writes. Stop on failure, report each target's observed effect, and refresh reads before retrying. Preserve successful earlier effects in that report. This grants no PR-branch deletion authority.

**Gated merge preparation.** Use `rerun` after a terminal outcome or once the monitor has stopped. A residual monitor after completed `checks-passed` validation also permits a full merge-preparation rerun when all these conditions hold:

- No validation gate remains unresolved, and no validation or fix agent is active.
- The caller worktree is clean, and its head equals the head the gate selects for `rerun`.
- The selected head retains every prior gate fix. The rerun retains the accepted user intent.
- The installed command refuses a clean caller head mismatch before supersession, supports same-branch supersession, and preserves the accepted explicit intent, closing references, existing open PR identity, prior `--no-publish-intent` decision, branch custody, and every prior gate fix.

While a run or its monitor remains live and the completed-validation prerequisites above do not hold, leave the branch to the pipeline, report the needed rerun, and hold.

For this completed-validation case, this pstack rule replaces guidance that requires the residual monitor to stop. Continue following the installed tool's active-gate and custody rules. Inspect current AXI status and `branch_sync` before acting. Follow an offered custody synchronization before checking head equality. This exception permits only the supported full rerun between completed validation rounds. It never permits local commits while the pipeline owns the branch or a rerun to evade a finding or approval gate. Preserve existing exceptions and skips as evidence, and retain all hard gates and countersigns. Do not add a skip or override to make merge preparation pass.

Preserve an exception as history, then check its actual human authority and approved gap before applying it now. History does not extend approval to added scenarios, failed operations, changed relevant instructions, or changed proof obligations. Missing authority remains a gap. A source annotation change alone is not a change to authoritative intent content. Before fresh validation, restore its required verification inputs through supported controls and verify that their readable contents match the intended inputs. Absent, unreadable, or mismatched inputs remain gaps. Report any external recovery as external evidence, not native inheritance.

Record the old run ID before `rerun`. After it starts the replacement, inspect the old run with `no-mistakes axi status --run <old-run-id>`. The replacement may already be executing when `rerun` returns. Require positive terminal confirmation before further owner actions or a readiness claim. A cancellation request, elapsed wait, or replacement run ID alone is insufficient. If the old run remains active or its state is unknown, hold and report it. Confirm that the replacement preserves the accepted explicit intent, closing references, existing open PR identity, prior `--no-publish-intent` decision, branch custody, and every prior gate fix. Drive fresh validation and CI on the replacement head. Require clean new validation for a clean merge-ready claim. Keep prior exceptions in the history, then recheck the independent verdict and merge authorization. Never substitute a manual abort, rebase, force-push, or monitor-timeout edit for this protocol.

**Attachments.** Upload through the forge CLI, not a browser you drive yourself. With Origin, use its attach flag when `origin pr create --help` lists one. Otherwise, for a GitHub repository, use `gh`, whichever CLI opened the PR. Pass `--attach <path>` to `gh pr create`, `gh pr edit`, or `gh pr comment`, once per file, with alt text after `#` (`--attach './login.png#The login error'`). A body that references the local path, such as `![alt](./login.png)`, gets that reference rewritten to the upload. `--attach` needs gh 2.99.0 or later and push access. When `gh pr edit --help` does not list it, run a gh at 2.99.0 or later. Do not upload through undocumented endpoints. When the forge CLI rejects the upload, as `gh --attach` can on Enterprise, record a CLI limitation. It does not show that the repository forbids attachments. Do not retry the route. When the user has authorized a manual upload, ask them to upload the file through the web UI and paste back the attachment URL or `<img>` markup. Otherwise report the upload as unavailable.

For github.com or GHES attachments with the `https://<host>/user-attachments/assets/` URL shape, use the PR's host and its token. After posting, read the PR back with `gh pr view <number> -R <host>/<owner>/<repo> --json body,comments` and request each attachment URL with `curl -s -o /dev/null -w '%{http_code}' -L -H "Authorization: Bearer $(gh auth token --hostname <host>)" <url>`. It must return `200`. A signed-out request can fail on a working upload, so it proves nothing. After a successful CLI upload, when its URL does not return `200`, attach the file again once. A CLI rejection follows the fallback above without another CLI attempt. Report upload availability, the saved PR content, and the authenticated fetch result separately; include the gh version and any error. For recap sketches, follow [pr-recap's posting and render checks](../../pr-recap/SKILL.md#post-or-update-the-comment).

**Built-in PR tool.** In a gated repository, follow **Gated publish** instead. When the run provides a built-in PR tool, create, edit, retarget, and mark ready through it, never through a forge CLI. A CLI-made PR misses what the tool tracks. Use the resolved forge for everything the tool does not cover, and for every PR operation when the run has no such tool.

**Size and stacks.** Prefer five narrow PRs to one large PR. In a gated repository, build stacks through **Gated publish**. A stack is a base-branch chain. The root PR targets trunk. Each child branch rebases onto its parent's exact tip and its PR targets the parent branch. As a parent merges, move its child onto trunk per steps 4 and 7 of `playbooks/shipping.md`. Without a built-in PR tool, per the resolved forge, create a child with `origin pr create --status open --base <parent-branch>` or `gh pr create --base <parent-branch>`, and retarget one with `origin pr edit <pr> --base <parent-branch>` or `gh pr edit <pr> --base <parent-branch>`. Branch from trunk only for independent work. Rebase on trunk before substantial stack work.

**Readiness.** Open every PR ready, never as a draft. A built-in PR tool can default to draft, so set `draft: false` on every creation call through it. With Origin, pass `--status open`. With `gh`, omit `--draft`. If a PR still opens as a draft, mark it ready through the PR tool, or run `origin pr ready <number>` or `gh pr ready <number>` according to the resolved forge. Run `origin pr view <number>` or `gh pr view <number>` before you refer to PR status.

For upstream-sync publication routes and draft requirements, follow [Syncing from upstream](../../../PORTING.md#syncing-from-upstream).

**Recap.** After a PR opens, use the **pr-recap** skill. For post-push refresh timing, follow [task triggers](../references/task-triggers.md).

**Babysit.** Opening a PR does not start a babysit. Post the URL and keep building. Finish the phase or stack first. Run a separate babysit pass only when the user asks for one after the whole stack exists. A babysit for each new PR stalls the build and spends checks on commits later waves restart. Push back when feedback drifts from intent.

A subagent that opens a PR uses the **interrogate** skill, the **deslop** skill, and the **no-comments** skill, and posts the URL. A non-owner subagent finalizes the body per **Descriptions** before it posts the URL. It returns to the parent without babysitting, unless it is an Autopilot-full or Autopilot-stack owner. That owner's brief assigns the babysit loop and is the ask `playbooks/babysit.md` waits for. The owner starts the loop after its code-ready report, reports merge-ready or STACK-READY per its playbook, and is exempt from the rules here and in `playbooks/babysit.md` that hold babysitting until a whole stack is built.
