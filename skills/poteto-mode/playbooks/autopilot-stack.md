### Autopilot-stack

**You own the verdicts, never the landing. Run Autopilot-full without the merge. Build and verify the queue with full autonomy, then hand the operator the verified PRs to review and land. A PR stacks only on a PR it builds on.** **Autopilot-full** holds except for how verified work leaves. Each tick re-reads both playbooks from trunk, and this one wins where they differ.

**Choosing between the autopilots.** Autopilot-full when the run may merge. Autopilot-stack when the operator lands the PRs.

1. **Run the owner loop unchanged.** In a gated repository, owners and the root follow the gated publish rules in `playbooks/opening-a-pr.md`. Use the **pstack-harness** skill to resolve the portable roots. Keep their concrete values in private, untracked run state and pass them to every owner. Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One background agent per PR (its own isolated worktree) owns its change end to end: build, first push, a ready PR opened before self-proof, self-proof (gates, CI, receipts), skeptical Bugbot triage per `../references/bugbot-triage.md`, the **deslop** skill before every commit or amend per its [Before each commit](../../deslop/SKILL.md#before-each-commit) check, with evidence returned to the root, a comment review with the **no-comments** skill, and babysit to green per `playbooks/babysit.md`. Owners parallelize when the work is self-contained, and those items branch off trunk per Autopilot-full step 3. When an item builds on another, its owner branches from that item's branch, not from trunk. Within about 15 minutes, every owner uses the **show-me-your-work** skill to start a `decisions.tsv` trail, pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes each finished unit before it starts the next (hooks on, a WIP commit is fine). Keep the trail uncommitted and return it in the report. Owners also keep the `children.tsv` of Autopilot-full step 2.
2. **Audit on a real loop.** The root runs an audit tick every hour. On the operator's go, the root arms the tick through the harness's loop facility with a prompt that runs this tick, per Autopilot-full step 6. In Claude Code that is `/loop 1h`. Never leave the cadence to memory or lossy completion notifications. Restore the recorded roots at each tick. Re-read this playbook from trunk with `git -C "${PSTACK_SOURCE_ROOT:?}" fetch origin '+refs/heads/main:refs/remotes/origin/main' && git -C "$PSTACK_SOURCE_ROOT" show 'origin/main:skills/poteto-mode/playbooks/autopilot-stack.md'` and audit the operation against it. Fix drift during that tick. If that fetch fails, skip the drift fix for this tick, run the rest of the tick, and record the failed fetch in the trail. Probe each owner with a generic liveness or status check. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that passes its expected runtime without a side effect as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. Probe all subagents and end the tick per Autopilot-full step 6.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. The root verifies each round per Autopilot-full step 4, with STACK-READY in place of merge-ready. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. Owners never rebase onto another branch, trunk included, and never retarget a PR, because the root owns the chain's topology and the operator owns the landing. A clean verdict appends a PR that builds on another PR to that PR's stack, in dependency order. Every other PR keeps trunk as its base.
6. **Single writer on topology, parallel writers on builds.** In a gated repository, follow the gated publish rules in `playbooks/opening-a-pr.md` for every push and restack below. Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer, because two writers on one chain undo each other. An owner takes the root's push as its new base and lease. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, push with `--force-with-lease` only after an `ls-remote` check, and set the PR base to the parent branch. Create it with `origin pr create --status open --base <parent-branch>` or `gh pr create --base <parent-branch>` according to the resolved forge. Retarget an existing PR with `origin pr edit <pr> --base <parent-branch>` or `gh pr edit <pr> --base <parent-branch>`. Only a stack's root PR targets trunk. Never submit or register the chain through `gt`.
7. **Absorb drift at the root, then re-verify what moved.** In a gated repository, the root absorbs drift through the gated `rerun` rule in `playbooks/opening-a-pr.md`. The root fetches current trunk, applies Autopilot-full step 5's rebase test to each link, and rebases each chain from bottom to top where that test calls for one. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at the old SHAs. Apply the patch-id rule in `playbooks/shipping.md` at each verdict SHA. A link's base is its parent, so its patch-id covers only its own diff. Anything that is no longer valid goes back through this playbook's step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the PRs.** The deliverable is the verified PRs, each stack reviewable bottom-up in the resolved forge, every PR carrying its verifier verdict in the PR body or a comment. After the handoff, nobody pushes without the operator's go. The operator reviews and lands them, with their own clicks or by arming merge-when-ready. Once landing starts, nobody writes to the chain except the post-merge retarget that `playbooks/shipping.md` sanctions, because a second writer breaks a landing in flight. A mid-landing problem goes through the root to the operator, and any fix waits for the operator's go.

**Reply:** Use the **ketchup** skill. Catch the operator up with each PR, its link, and a one-line verdict, each stack's root and tip, and anything parked or excluded with the reason.
