# Apply task triggers

- First message → restate the user's goal and the smallest change you expect to meet it, then proceed. Open each subagent brief, PR `## Why`, and final report with the goal.
- A fork you could settle by running something → prototype it per the Prototype playbook (`../playbooks/prototype.md`) instead of asking.
  - For a suspected bug, reproduce it on the real system before presenting it as an operator decision. If reproduction is unavailable, report the suspicion and the evidence gap.
  - Apply [authorization](authorization.md) to irreversible actions and operator gates.
- Code → name the data shape first.
- Writing acceptance tests or criteria for a new requirement from a spec, issue, or plan → call the Skill tool with `spec-probes`, then follow its Before code steps.
- Code that crosses two or more source files and admits several plausible shapes → call the Skill tool with `architect` for the shape before implementing. In Bug fix, Feature, Refactoring, and Perf issue this applies on the intensive route only. On their standard route, compare the shapes yourself in a table and raise the route when you cannot choose. Feature chooses its route from risk evidence, not module count. For a bug fix, skip architect when runtime evidence confirms the root cause and identifies one localized repair, even across a function boundary. Go straight to the failing reproducer, then repair it. Keep architect when design choices or repair scope remain unresolved.
- Fan-out or a bakeoff, outside a routed playbook's lightweight or standard route → for fan-out, call the Skill tool with `swarm`. For a bakeoff, call the Skill tool with `arena`.
- About to wait for a human reply, or to answer a no-mistakes gate → read [unattended runs](unattended.md) first.
- Contested design → call the Skill tool with `interrogate`. On a routed playbook's standard route, record the disagreement and your choice in the reply instead.
- Prose, your reply included → call the Skill tool with `unslop`. Before a PR title or body is published, run `python3 "${PSTACK_SKILLS_ROOT:?}/poteto-mode/scripts/check-writing.py"` on it and fix what it reports.
- Docs, PR descriptions, or commit messages → call the Skill tool with `technical-writing`.
- Before reporting a substantive code or public workflow change complete → call the Skill tool with `documentation-impact` in `author` mode. This applies without a PR, except on the lightweight route, whose result comes from Babysit. Status-only workflows report a missing or stale author result or a missing or stale required independent review verdict as pending without starting either pass.
- Before each push or published head → call the Skill tool with `deslop`. On the intensive route, in a machine-consumed playbook, and wherever a brief says so, do this before every commit or amend instead. Complete its [Before each commit](../../deslop/SKILL.md#before-each-commit) check over the commits in that scope, including the evidence. Then call the Skill tool with `unslop` over code comments, names, and messages, which are prose surfaces too.
- Starting a review of your own change, such as a doc review or a review of a delegate's diff → ask the reviewer for every finding in one pass. Repair the findings in one round, then recheck that repair. Rerun the full review instead when the repair changes behavior or contract claims. Report the recheck's notes in your reply. If the recheck does not pass, report completion as pending with its open findings instead of starting another round. Autopilot and Shipping verdict rounds keep their own stop rules.
- Before review → call the Skill tool with `no-comments`.
- Shipping UI / IDE / CLI → use the project's verification skill (`verify-<app>`, generated by the **create-verification-skill** skill).
- A number you measured → call the Skill tool with `benchmark-checklist`.
- PR status → the **Babysit** playbook (`../playbooks/babysit.md`), not any built-in babysit skill your CLI ships. Landing a green stack → the **Shipping** playbook (`../playbooks/shipping.md`).
- The user or the repository's contributor instructions ask for PR recaps → after a PR opens or its diff changes, call the Skill tool with `pr-recap`. Without that ask, post no recap. An operator's hold or zero-writes order wins: post no recap, and report the refresh as pending until the operator releases the hold.
- Bot review comments → judge each on its merits.
- Explicit `show-me-your-work` invocation, unattended work, a loop run, or any task the user steps away from to review later ("going to bed", "trust it when i'm back", "/loop until X") → call the Skill tool with `show-me-your-work` for a decision trail.
