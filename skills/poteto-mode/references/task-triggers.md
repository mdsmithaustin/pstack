# Apply task triggers

Read this reference for the actions named by the mode entry, or when scope changes. Apply only the triggers that match the next work.

- Your first message on a task → tell the user, in your own words, their goal, the problem they are solving, and, if the task ships a change, the smallest change you expect to meet it. Don't wait for confirmation. If the evidence rules out the change the user asked for, show it and stop. Restate the user's goal in each subagent brief, and open each PR's `## Why` with it. Open each final report with it too, your final reply included, except after a fully specified one-line edit.
- Nontrivial change, architecture decision, or "are we sure?" → call the Skill tool with `how`.
- About to `AskQuestion` on a "which approach", "how should I", or "what should this do" fork → classify it before you ask. If the answer is a fact you could observe by running something (behavior, timing, layout, output, perf, even whether an eval separates), it is not the human's to answer. For a suspected bug, reproduce it on the real system before presenting it as an operator decision. If reproduction is unavailable, report the suspicion and the evidence gap. Sketch other observable forks via the Prototype playbook (`../playbooks/prototype.md`) and let the result decide. If the task is a read-only Investigation or Research whose deliverable is a cited answer, stay in it and answer from the evidence rather than building a sketch. Reserve the question for a genuine product or preference call no experiment can settle. Under a full-autonomy grant, decide a call the grant covers, act on it, and report it, with no reply word and no offer. Under the grant, for a call only the operator can make, apply a default, report it with a full explanation, and say in plain words what the operator could tell you to do instead. The operator answers in their own words. Never give a shorthand token to type back. Gates the operator named and the Always-pause list in Autonomy still need the operator.
- Any code → name the data shape first. Call the Skill tool with `principle-model-the-domain` to choose its organizing structure.
- Writing acceptance tests or criteria for a new requirement from a spec, issue, or plan → call the Skill tool with `spec-probes`, then follow its edge probe. List the edges each requirement's data shape raises, such as boundary values, empty input, ordering, and encoding. Settle each edge from the spec text, or from the current code's behavior when the spec is silent. Test each settled edge, or dismiss it with a reason when no test fits. Report each edge neither settles as an open gap, not a test.
- Code crossing a function boundary → call the Skill tool with `architect` for parallel design exploration before implementing. For a bug fix, skip architect when runtime evidence confirms the root cause and identifies one localized repair, even across a function boundary. Go straight to the failing reproducer, then repair it. Keep architect when design choices or repair scope remain unresolved.
- Parallel fan-out → call the Skill tool with `swarm` for coverage matrices, races, gauntlets, and exploration partitions. Call the Skill tool with `arena` for design or code bakeoffs with base selection and grafting.
- Any subagent spawn → call the Skill tool with `pstack-harness`. Its **Spawn a role** section resolves the role's model and effort and maps them to this CLI. A structured question, when unsure how this CLI asks one → use the same skill.
- About to wait for a human reply, or to answer a no-mistakes gate → read [unattended runs](unattended.md) first.
- Contested design → call the Skill tool with `interrogate` (multi-model adversarial) before shipping.
- Nontrivial multi-step → write the throughput checkpoint (Feature step 3).
- Any prose surface, your reply to the user included → call the Skill tool with `unslop`. Write the reply per [writing](writing.md). Agent-facing prose also follows the authoring guidance in `../playbooks/authoring-a-skill.md`.
- Docs, RFCs, readmes, PR descriptions, or commit messages → call the Skill tool with `technical-writing`.
- Before reporting a substantive code or public workflow change complete → call the Skill tool with `documentation-impact` in `author` mode. Use its author result to decide whether fresh independent review is required. When the result is `independent review required`, start a different-agent review on the `trail reviewer` role and do not report completion until its current verdict is `pass`; repair findings and repeat the review otherwise. Carry the prior review and repair evidence into each recheck, using documentation-impact's repair scope and freshness rules. This applies without a PR. For read-only audits, use `review` mode and report gaps without repairs. Status-only workflows report a missing or stale author result or a missing or stale required independent review verdict as pending without starting either pass.
- Before every commit or amend → call the Skill tool with `deslop`. Complete its [Before each commit](../../deslop/SKILL.md#before-each-commit) check, including the full read and evidence, before committing. Then call the Skill tool with `unslop` over code comments, names, and messages, which are prose surfaces too.
- Before review → call the Skill tool with `no-comments`.
- Shipping UI / IDE / CLI → use the project's verification skill (`verify-<app>`, generated by the **create-verification-skill** skill), which drives the real surface — browser, Electron, web UI, CLI, or TUI. For bug fixes, reproduce first on the same surface yourself. Hand to the user only under the narrow Bug fix step 1 exception.
- Running a benchmark, measuring perf yourself, or reporting a speedup or regression you measured → call the Skill tool with `benchmark-checklist` before you report or act on the number.
- Any PR-status request ("babysit this", "get it green", "address the bugbot comments", and most often "check on PR X" or "anything outstanding on X") → the **Babysit** playbook (`../playbooks/babysit.md`), not any built-in babysit skill your CLI ships, even when its description matches the same words. Never triggered by merely opening a PR. Declare its mode before polling. The playbook's step 1 owns the request-to-mode mapping. Reaching for `drive` inside a phase agent stops that agent finishing its turn.
- A push changed an open PR's diff, whether yours, an Autopilot owner's, a Babysit or Shipping wave, or a gate fix round → once the new head is published and any gate run has reached its outcome, call the Skill tool with `pr-recap` to refresh the PR's recap. A `threads-only` Babysit fix push refreshes it like any other push. An operator's hold or zero-writes order wins: post no recap, and report the refresh as pending until the operator releases the hold.
- Asked to land or ship a green stack → the **Shipping** playbook (`../playbooks/shipping.md`). Green is not safe. Nothing gets armed before an independent per-PR verdict, and only the contiguous verified run from the root lands.
- Bugbot, Copilot code review, GitHub Advanced Security, or another automated security reviewer commented → skeptical posture. They catch real bugs and also file non-issues and nitpicks, so assess each on its merits and dismiss noise with a concrete reason instead of churning code. Triage fix / dismiss / ask per `bugbot-triage.md`.
- Broken skill mid-task → fix it in its own PR. Don't block. Don't silently work around it.
- Explicit `show-me-your-work` invocation, unattended work, a loop run, or any task the user steps away from to review later ("going to bed", "trust it when i'm back", "/loop until X") → call the Skill tool with `show-me-your-work` for a decision trail. Multiple phases alone do not require a trail. That skill owns the logging and evidence-retention rules.
