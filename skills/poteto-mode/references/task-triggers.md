# Apply task triggers

Read this reference for the actions named by the mode entry, or when scope changes. Apply only the triggers that match the next work. Apply the plan's route before dispatching skills or agents. On the lightweight route, load only the skills the plan lists and spawn no investigation or implementation delegate. The independent reviewer in the review lens is not such a delegate. In Bug fix, Feature, Refactoring, and Perf issue, `architect`, `arena`, `swarm`, and `interrogate` load only on the intensive route. Every other playbook keeps the panels its own steps require, such as Eval's `arena` and Autopilot-full's `swarm`. If the risk facts no longer hold, rerun the plan script first, as [routes](routes.md) says.

- Your first message on a task → tell the user, in your own words, their goal, the problem they are solving, and, if the task ships a change, the intended change to meet it. Don't wait for confirmation. If the evidence rules out the change the user asked for, show it and stop. Restate the user's goal in each subagent brief, except the briefs of the test delegate and the read-only reviewer in Feature steps 4 and 7. Open each PR's `## Why` with the goal. Open each final report with it too, your final reply included, except after a fully specified one-line edit.
- Nontrivial change, architecture decision, or "are we sure?" → call the Skill tool with `how`.
- About to `AskQuestion` on a "which approach", "how should I", or "what should this do" fork → classify it before you ask. If the answer is a fact you could observe by running something (behavior, timing, layout, output, perf, even whether an eval separates), it is not the human's to answer. For a suspected bug, reproduce it on the real system before presenting it as an operator decision. If reproduction is unavailable, report the suspicion and the evidence gap. Sketch other observable forks via the Prototype playbook (`../playbooks/prototype.md`) and let the result decide. If the task is a read-only Investigation or Research whose deliverable is a cited answer, stay in it and answer from the evidence rather than building a sketch. Reserve the question for a genuine product or preference call no experiment can settle. Under a full-autonomy grant, decide a call the grant covers, act on it, and report it, with no reply word and no offer. Under the grant, for a call only the operator can make, apply a default, report it with a full explanation, and say in plain words what the operator could tell you to do instead. The operator answers in their own words. Never give a shorthand token to type back. Apply [authorization](authorization.md) to irreversible actions and operator gates.
- Any code → name the data shape first. Call the Skill tool with `principle-model-the-domain` to choose its organizing structure.
- Writing acceptance tests or criteria for a new requirement from a spec, issue, or plan → call the Skill tool with `spec-probes`, then follow its edge probe. List the edges each requirement's data shape raises, such as boundary values, empty input, ordering, and encoding. Settle each edge from the spec text, or from the current code's behavior when the spec is silent. A new rejection, error, or reinterpretation of input needs a requirement that states the restriction, even on a new field. Test each settled edge, or dismiss it with a reason when no test fits. Report each edge neither settles as an open gap, not a test.
- Code that crosses two or more source files and admits several plausible shapes → call the Skill tool with `architect` for parallel design exploration before implementing. In Bug fix, Feature, Refactoring, and Perf issue this applies on the intensive route only. On their standard route, compare the shapes yourself in a table and raise the route when you cannot choose. Feature chooses compact execution from risk evidence, not module count. For a bug fix, skip architect when runtime evidence confirms the root cause and identifies one localized repair, even across a function boundary. Go straight to the failing reproducer, then repair it. Keep architect when design choices or repair scope remain unresolved.
- Parallel fan-out, outside a routed playbook's lightweight or standard route → call the Skill tool with `swarm` for coverage matrices, races, gauntlets, and exploration partitions. Call the Skill tool with `arena` for design or code bakeoffs with base selection and grafting.
- Any subagent spawn → call the Skill tool with `pstack-harness`. Its **Spawn a role** section resolves the role's model and effort and maps them to this CLI. A structured question, when unsure how this CLI asks one → use the same skill.
- About to wait for a human reply, or to answer a no-mistakes gate → read [unattended runs](unattended.md) first.
- Contested design → call the Skill tool with `interrogate` (multi-model adversarial) before shipping. On a routed playbook's standard route, record the disagreement and your choice in the reply instead.
- Nontrivial multi-step → write the throughput checkpoint (Feature step 5). The lightweight route may omit it for serial direct work.
- A gate the plan prints → run it at the time the plan states. With no plan, run cleanup before every commit or amend, which is the gate skills' own default. With no plan, also take the endpoint from [routes](routes.md#endpoint), and follow the review lens's [Independent scrutiny](review-lens.md#independent-scrutiny) section before you report a code change complete.
- Any prose surface, your reply to the user included → call the Skill tool with `unslop`. Write the reply per [writing](writing.md). Before a PR title or body is published, run `python3 "${PSTACK_SKILLS_ROOT:?}/poteto-mode/scripts/check-writing.py"` on it and fix what it reports. Agent-facing prose also follows the authoring guidance in `../playbooks/authoring-a-skill.md`.
- Docs, RFCs, readmes, PR descriptions, or commit messages → call the Skill tool with `technical-writing`.
- Before reporting a substantive code or public workflow change complete → call the Skill tool with `documentation-impact` in `author` mode. Use its author result to decide whether fresh independent review is required. When the result is `independent review required`, start a different-agent review on the `trail reviewer` role and do not report completion until its current verdict is `pass`. Repair findings in the one round that documentation-impact allows. Carry the prior review and repair evidence into the recheck, using documentation-impact's repair scope and freshness rules. If the recheck does not return `pass`, report completion as pending with its open findings instead of starting another round. This applies without a PR. For read-only audits, use `review` mode and report gaps without repairs. Status-only workflows report a missing or stale author result or a missing or stale required independent review verdict as pending without starting either pass.
- Before each push or published head → call the Skill tool with `deslop`. On the intensive route, in a machine-consumed playbook, and wherever a brief says so, do this before every commit or amend instead. Complete its [Before each commit](../../deslop/SKILL.md#before-each-commit) check over the commits in that scope, including the evidence. Then call the Skill tool with `unslop` over code comments, names, and messages, which are prose surfaces too.
- Starting a review of your own change, such as a doc review or a review of a delegate's diff → ask the reviewer for every finding in one pass. Repair the findings in one round, then recheck that repair. Rerun the full review instead when the repair changes behavior or contract claims. Report the recheck's notes in your reply. If the recheck does not pass, report completion as pending with its open findings instead of starting another round. Autopilot and Shipping verdict rounds keep their own stop rules.
- Before review, when the diff adds or changes comments, doc comments, docstrings, or lint or type suppressions → call the Skill tool with `no-comments`.
- Shipping UI / IDE / CLI → use the project's verification skill (`verify-<app>`, generated by the **create-verification-skill** skill), which drives the real surface — browser, Electron, web UI, CLI, or TUI. For bug fixes, reproduce first on the same surface yourself. Hand to the user only under the narrow Bug fix step 1 exception.
- Running a benchmark, measuring perf yourself, or reporting a speedup or regression you measured → call the Skill tool with `benchmark-checklist` before you report or act on the number.
- Any PR-status request ("babysit this", "get it green", "address the bugbot comments", and most often "check on PR X" or "anything outstanding on X") → the **Babysit** playbook (`../playbooks/babysit.md`), not any built-in babysit skill your CLI ships, even when its description matches the same words. Never triggered by merely opening a PR. Declare its mode before polling. The playbook's step 1 owns the request-to-mode mapping. Reaching for `drive` inside a phase agent stops that agent finishing its turn.
- The user or the repository's contributor instructions ask for PR recaps → after a PR opens, and after a push changes its diff once the new head is published and any gate run has reached its outcome, call the Skill tool with `pr-recap`. Without that ask, post no recap. An operator's hold or zero-writes order wins: post no recap, and report the refresh as pending until the operator releases the hold.
- Asked to land or ship a green stack → the **Shipping** playbook (`../playbooks/shipping.md`). Green is not safe. Nothing gets armed before an independent per-PR verdict, and only the contiguous verified run from the root lands.
- Bugbot, Copilot code review, GitHub Advanced Security, or another automated security reviewer commented → skeptical posture. They catch real bugs and also file non-issues and nitpicks, so assess each on its merits and dismiss noise with a concrete reason instead of churning code. Triage fix / dismiss / ask per `bugbot-triage.md`.
- Broken skill mid-task → fix it in its own PR. Don't block. Don't silently work around it.
- Explicit `show-me-your-work` invocation, unattended work, a loop run, or any task the user steps away from to review later ("going to bed", "trust it when i'm back", "/loop until X") → call the Skill tool with `show-me-your-work` for a decision trail. Multiple phases alone do not require a trail. That skill owns the logging and evidence-retention rules.
