# Apply task triggers

Read this reference when the mode entry names an action or scope changes. Before dispatch, apply the plan's route and only the triggers for the next work. For lightweight work, follow the [local, push, and PR rules](routes.md#the-three-routes). Spawn no investigation or implementation delegate on that route. Keep independent review under the review lens. The lightweight plan has no documentation gate, so its `documentation-impact` result comes from Babysit or Shipping. In Bug fix, Feature, Refactoring, and Perf issue, `architect`, `arena`, `swarm`, and `interrogate` load only on the intensive route. Every other playbook keeps the panels its own steps require, such as Eval's `arena` and Autopilot-full's `swarm`. If the risk facts no longer hold, rerun the plan script first, as [routes](routes.md) says.

- First message → restate the user's goal and the intended change that meets it, then proceed. Open each subagent brief, PR `## Why`, and final report with the goal, except the briefs of the test delegate and the read-only reviewer in Feature steps 4 and 7.
- Nontrivial change, architecture decision, or "are we sure?" → call the Skill tool with `how`.
- A fork you could settle by running something → prototype it per the Prototype playbook (`../playbooks/prototype.md`) instead of asking.
  - For a suspected bug, reproduce it on the real system before presenting it as an operator decision. If reproduction is unavailable, report the suspicion and the evidence gap.
  - If the task is read-only Research whose deliverable is a cited answer, stay in it and answer from the evidence rather than building a sketch.
  - Apply [authorization](authorization.md) to irreversible actions and operator gates.
- Code → name the data shape first.
- Writing acceptance tests or criteria for a new requirement from a spec, issue, or plan → call the Skill tool with `spec-probes`, then follow its Before code steps. List the edges each requirement's data shape raises, such as the unit counted, boundary values, and empty input. Settle each edge from the spec text, or from the current code's behavior when the spec is silent. A new rejection, error, or reinterpretation of input needs a requirement that states the restriction, even on a new field. Test each settled edge, or dismiss it with a reason when no test fits. Report each edge neither settles as an open gap, not a test.
- Code that crosses two or more source files and admits several plausible shapes → call the Skill tool with `architect` for parallel design exploration before implementing. In Bug fix, Feature, Refactoring, and Perf issue this applies on the intensive route only. On their standard route, compare the shapes yourself in a table and raise the route when you cannot choose. Feature chooses its route from risk evidence, not module count. For a bug fix, skip architect when runtime evidence confirms the root cause and identifies one localized repair, even across a function boundary. Go straight to the failing reproducer, then repair it. Keep architect when design choices or repair scope remain unresolved.
- Fan-out or a bakeoff, outside a routed playbook's lightweight or standard route → for fan-out, call the Skill tool with `swarm`. For a bakeoff, call the Skill tool with `arena`.
- Any subagent spawn → call the Skill tool with `pstack-harness`. Its **Spawn a role** section resolves the role's model and effort and maps them to this CLI. A structured question, when unsure how this CLI asks one → use the same skill.
- About to wait for a human reply, or to answer a no-mistakes gate → read [unattended runs](unattended.md) first.
- Contested design → call the Skill tool with `interrogate`. On a routed playbook's standard route, record the disagreement and your choice in the reply instead.
- A gate the plan prints → run it at the time the plan states. With no plan, run cleanup before every commit or amend, which is the gate skills' own default. With no plan, also take the endpoint from [routes](routes.md#endpoint), and follow the review lens's [Independent scrutiny](review-lens.md#independent-scrutiny) section before you report a code change complete.
- Prose, your reply included → call the Skill tool with `unslop`. Before a PR title or body is published, run `python3 "${PSTACK_SKILLS_ROOT:?}/poteto-mode/scripts/check-writing.py"` on it and fix what it reports.
- Docs, PR descriptions, or commit messages → call the Skill tool with `technical-writing`.
- Before reporting a substantive code or public workflow change complete → call the Skill tool with `documentation-impact` in `author` mode. Use its author result to decide whether fresh independent review is required. When the result is `independent review required`, start a different-agent review on the `trail reviewer` role and do not report completion until its current verdict is `pass`. This applies without a PR, except on the lightweight route, whose result comes from Babysit or Shipping. For read-only audits, use `review` mode and report gaps without repairs. Status-only workflows report a missing or stale author result or a missing or stale required independent review verdict as pending without starting either pass.
- Repairing documentation-impact findings → repair them in the one round that documentation-impact allows. Carry the prior review and repair evidence into the recheck, using documentation-impact's repair scope and freshness rules. If the recheck does not return `pass`, report completion as pending with its open findings instead of starting another round.
- Before each push or published head → call the Skill tool with `deslop`. On the intensive route, in a machine-consumed playbook, and wherever a brief says so, do this before every commit or amend instead. Complete its [Before each commit](../../deslop/SKILL.md#before-each-commit) check over the commits in that scope, including the evidence. Then call the Skill tool with `unslop` over code comments, names, and messages, which are prose surfaces too.
- Starting a review of your own change, such as a doc review or a review of a delegate's diff → ask the reviewer for every finding in one pass. Repair the findings in one round, then recheck that repair. Rerun the full review instead when the repair changes behavior or contract claims. Report the recheck's notes in your reply. If the recheck does not pass, report completion as pending with its open findings instead of starting another round. Autopilot and Shipping verdict rounds keep their own stop rules.
- Before review, when the diff adds or changes comments, doc comments, docstrings, or lint or type suppressions → call the Skill tool with `no-comments`.
- Shipping UI / IDE / CLI → use the project's verification skill (`verify-<app>`, generated by the **create-verification-skill** skill).
- A number you measured → call the Skill tool with `benchmark-checklist`.
- PR status → the **Babysit** playbook (`../playbooks/babysit.md`), not any built-in babysit skill your CLI ships. Landing a green stack → the **Shipping** playbook (`../playbooks/shipping.md`).
- The user or the repository's contributor instructions ask for PR recaps → after a PR opens, and after a push changes its diff once the new head is published and any gate run has reached its outcome, call the Skill tool with `pr-recap`. Without that ask, post no recap. An operator's hold or zero-writes order wins: post no recap, and report the refresh as pending until the operator releases the hold.
- Bot review comments → judge each on its merits.
- Explicit `show-me-your-work` invocation, unattended work, a loop run, or any task the user steps away from to review later ("going to bed", "trust it when i'm back", "/loop until X") → call the Skill tool with `show-me-your-work` for a decision trail. Multiple phases alone do not require a trail. That skill owns the logging and evidence-retention rules.
