# Recover a usage-limit interruption

Use this procedure from the Autopilot-full audit tick when a provider reports a usage or quota limit. Record the provider error and its source. A limit interruption leaves the affected work pending. It proves neither a change failure nor a passing lane. Keep test failures, review findings, policy refusals, and unknown causes separate.

1. Save the affected owner, child IDs, exact roles and one-based arms, briefs, standing orders, checkouts, resolution context, observed execution identities, last completed work, and current states in the existing private registry and decision trail. Include affected no-mistakes run IDs and steps. Follow the harness's role-handoff contract. Preserve prior evidence and retry allowances.
2. Record the provider's reset time with its timezone and source. If no reset time is available, record that gap and allow at most one bounded availability probe for the interruption, within the existing retry allowance. Persist its attempt and result across ticks and resumes. If it establishes neither availability nor a reset time, keep recovery blocked until either is observed. Another audit tick does not reset the probe allowance. For a known reset time, follow the harness's loop procedure to arm one actual one-shot wake at or after the reset. Record its job or receipt, trigger, recovery-state location, and responsible coordinator. A proposed schedule or a sleep that cannot re-enter the session owns no future work. If no scheduler or active re-invoking wrapper can own the wake, report that infrastructure block and keep recovery pending. Do not promise automatic recovery.
3. At the wake, or after the probe confirms availability, restore the saved roots and inspect provider availability and each affected child's current state. Keep completed results and leave live children alone. Try the harness's supported resume for each interrupted child using its saved role, arm, brief, and state. Resume only the saved interrupted attempt. New work and later review or fix rounds follow [delegation](delegation.md). If resume is unavailable or fails, confirm the old child cannot write before starting a fresh replacement through the delegation and role-resolution procedures. Record the new ID and execution identity without overwriting history. Unknown old-writer state holds replacement writes. Re-arm only for a newly reported provider reset time within the existing retry allowance. Elapsed time alone proves neither availability nor permission.
4. Inspect each affected gate through AXI status and its full failed-step log. Read the installed no-mistakes skill and command help before recovery. Follow `branch_sync.next_action` before changing the caller checkout. Never edit, abort, or rerun an active gate to take custody or bypass a finding.
5. When the installed command supports `no-mistakes axi retry --run <id>`, use it only for its eligible terminal agent invocation failure. Its current contract requires the latest run, no active run, no prior push, a failure at or before Test, unchanged configuration, and a clean caller at the exact preserved head. Adopt that head only through the offered guarded recovery. Retry restarts the failed step and carries eligible prior steps. A refusal leaves recovery pending. Inspect the failed proof and use the supported full rerun only when its between-run and custody rules permit it. Never substitute a retry for a change failure or invent a retry command for an older installation.
6. Drive the resulting run through the gated publish procedure with the accepted intent and every prior gate fix intact. Recheck current authority, protected paths, exceptions, and operator-reserved decisions. No recovery grants an approval, skip, override, direct push, or merge. Require fresh live proof and CI for the resulting head before readiness. Report resumed, replaced, completed, and still-blocked children separately from the gate's outcome.
