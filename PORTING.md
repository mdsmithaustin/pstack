# Porting notes

This is a port of [cursor/plugins/pstack](https://github.com/cursor/plugins/tree/main/pstack) (MIT, by [poteto](https://x.com/poteto)) from Cursor to a CLI-agnostic skill set that installs with [`npx skills`](https://skills.sh) and runs in Claude Code, Codex, and Hermes.

Upstream is the source of truth for the workflows themselves. This file records every systematic substitution so future syncs from upstream can reapply them.

## Port additions beyond substitution

- The Playbooks task selector in `skills/poteto-mode/SKILL.md` owns two optional Matt Pocock routes. Preserve their native fallbacks, including direct opening of a named map when possible, preliminary Investigation before a human wait when it cannot be opened, and return to the native selector for the full task. Preserve the gate that requires likely prevention of wrong work, contradictory decisions, or rework. Trust a selected companion's dependencies without adding adapters, copied workflows, schemas, state mirrors, or new skills.
- **documentation-impact** (`skills/documentation-impact/`) is a port addition for authoring and independently reviewing documentation affected by a change. Preserve its auto-invocable metadata, `tools/skill-trigger-cases.json` entry, README and guide entries, central Poteto completion trigger, and Babysit and Shipping readiness hooks during sync. Preserve its canonical author result rules. The pass covers local work without a PR and binds any required independent review verdict to the examined artifact and documentation context. Visual tools remain optional. Keep model selection and lifecycle orchestration in the calling workflow.
- Upstream's `tdd` and `teach` skills are renamed `poteto-tdd` and `poteto-teach` so a global install cannot clobber identically named skills a user already has; the bug-fix playbook, README, and guide reference the new names.
- poteto-mode carries a GSD coexistence rule: in a repo with `.planning/STATE.md`, project lifecycle (milestones, phases, planning, state) routes to the matching `/gsd-*` command and poteto-mode never writes `.planning/`; it keeps task-level execution rigor.
- The **pstack-harness** skill (see the substitution map) is new in this port. Its primitives include a **worklist adapter**. "Open a worklist" defines ordered items and their states, not a tool name. The agent inspects live capability descriptions, makes at most one semantic discovery query when the harness defers capabilities, and prefers native structured work tracking when it is available. If discovery finds none or any call is rejected, the agent stops trying that carrier for the rest of the task and maintains the same worklist through the harness's normal progress-update channel. Both are native carriers. Do not preserve product-specific task-tool names, exact-name lookup instructions, scratch task files, retries, or fallback narration during sync. A durable file is only for workflows that must resume across sessions. A companion universal rule, **named sibling skills are files**: most pstack skills are gated against model invocation and absent from the tool inventory, so cross-references like "the architect skill" or a principle leaf are satisfied by reading the sibling directory's SKILL.md from the installed skills root, never by reporting the skill missing or editing its gating; poteto-mode's Principles intro anchors the same rule inline.
- The **pstack-harness** skill owns the three-root runtime contract. `PSTACK_SKILLS_ROOT` comes from the logical path of the loaded harness skill and works without Git or network access. `PSTACK_SOURCE_ROOT` accepts only the configured HTTPS or SSH identity for `mdsmithaustin/pstack`. Physical symlink ancestry is only a source candidate. A copied install creates a private shallow clone when a fresh trunk read needs one, and the program removes only a generated directory with its ownership marker. `PROJECT_ROOT` stays separate for consumer control skills. A source resolution, identity, clone, fetch, or object failure stops the trunk read. Installed files are never its fallback. `tools/check-skill-content.py` rejects both runtime substitutions from upstream in every raw skill Markdown line, including fenced templates. Keep this contract and lint during future syncs.
- Codex does not honor `disable-model-invocation`, so every skill that sets it also carries `agents/openai.yaml` with `policy.allow_implicit_invocation: false` — the Codex-standard analog. The two flags must stay in sync: adding or removing one means adding or removing the other.
- Deliberate divergence from upstream #300: **how**, **why**, and **unslop** stay auto-invocable in this port (no `disable-model-invocation`, no `agents/openai.yaml`), because they own high-value automatic triggers in the maintainer's roster ("how does X work", motivation questions, prose cleanup). Do not reapply upstream's gating to these three on future syncs; `typescript-best-practices` and `make-bot-ui` keep it.
- Four sites carry a conditional GitNexus nudge, active only when `.gitnexus/` exists in the repo: the **how** skill (SKILL.md and `references/explorer-prompt.md`) seeds exploration with `gitnexus query`/`context`/`trace`; **blast-radius** seeds the change map with `gitnexus detect-changes`/`impact`; the **refactoring** playbook enumerates callers with `gitnexus impact`/`context` before a migration wave; and the Code review playbook's review lens lists a shared symbol's callers with `gitnexus impact`. Freshness-first policy: an existing index is refreshed with `gitnexus analyze --index-only` (incremental, no-op when up to date) before the graph is consulted — by the lead only, never from parallel arms (concurrent analyzes can corrupt the KuzuDB store). Creating a first index stays suggest-only. The code itself remains the source of truth: the index reflects the last analyzed commit and never sees uncommitted edits. No-op on hosts and repos without GitNexus.
- The GitHub watcher (`skills/poteto-mode/scripts/watch-pr`) treats every review bot alike, not only Cursor Bugbot: a thread carries `bot: { login, passes } | null`, and `READY` waits while a bot is still a requested reviewer (`WAITING` with `pending-review-bots`), which is how GitHub Copilot code review shows up before it posts. Repos without review bots see no change. Upstream still has `isBugbot`/`bugbotReviewPasses`; on sync, keep the port's shape and re-apply the babysit playbook and triage-reference wording.
- Two roles beyond upstream's roster: `trail reviewer` (the show-me-your-work reviewer; upstream says "a different model family", which has no answer inside one vendor) and `default` (the entry for a spawn whose skill names no role, shipped as `inherit-parent`). The harness skill's "No improvised models" rule sends every role-less spawn through `default`; on sync, keep both roles and the show-me-your-work wording that resolves through `trail reviewer` and steps down a tier when it matches the working model.
- The models config carries reasoning effort and per-harness sections (port addition, 2026-09): an entry is `model` or `model@effort`; `## codex`, `## claude-code`, and `## hermes` sections override the flat lines for that harness; precedence, the effort policy (floor `high`, `xhigh` for the hardest roles, `max`/`ultra` only when written), and the Codex alias translation (`fable` → `gpt-5.6-sol@max`, `opus` → `gpt-5.6-sol@xhigh`, `sonnet` → `gpt-5.6-terra@high`, `haiku` → `gpt-5.6-luna@high`) live in one place, the **pstack-harness** skill, and every reader points there instead of restating the layering. `skills/setup-pstack/scripts/check-models-config.py` lints the file (unknown roles, bad efforts, per-model effort support, duplicate roles and sections); `skills/setup-pstack/examples/pstack-models.md` is the shipped default and CI lints it. On sync, re-apply the one-phrase "with its configured effort per the **pstack-harness** skill" hook to any new reader upstream adds. Upstream's setup-pstack budget ask (upstream #366: `unlimited`, `large`, `medium`, `small`) ports onto this grammar: the budget rewrites the `@effort` suffix of every real entry, harness sections and suffixed aliases included, instead of the effort token inside a Cursor slug; `unlimited` pins `max`, which is upstream's `keep max` since upstream defaults sit at `max`; the port adds a fifth option, `default — keep as written`, that applies no budget, because one file is shared across CLIs and a Claude Code run, which passes no per-spawn effort, would otherwise rewrite only the other CLIs' lines; and the `# budget: <label> (<effort>)` comment is recorded in the file and read back by setup-pstack, never at runtime.
- The models config is layered workspace-first: a role line in `.agents/pstack-models.md` overrides `~/.agents/pstack-models.md`; setup-pstack preserves values it cannot validate (another harness's choices) and has a write-fallback ladder (shell tool → workspace file → print) for harnesses that cannot write to the home directory.

- The **Code review** playbook (`skills/poteto-mode/playbooks/code-review.md`) and its review lens (`skills/poteto-mode/references/review-lens.md`) are new in this port with no upstream counterpart. Upstream routes a review request to Investigation, where no step loads the design principles. Keep the Code review selector entry and the Investigation entry's pointer to it. The lens holds review questions and a smells table. The rule text stays in the principle leaves, scoped to review.
- **verify-commands** and **spec-probes** (`skills/verify-commands/`, `skills/spec-probes/`) are new in this port with no upstream counterpart. They carry the two pieces of judgment content retained when GSD was retired from the maintainer's stack: the failing-direction rule with the verify-command traps, and the edge and prohibition probes run at spec time. Both are auto-invocable; neither names a skill from another suite.
- **runtime-probes** (`skills/runtime-probes/`) is new in this port with no upstream counterpart. It is the running-system twin of **spec-probes** and also owns explicitly requested source-grounded handoffs when the target is unavailable. Keep its two modes distinct during sync: live work uses entry-point shapes and the closed taxonomy to generate bounded adversarial hypotheses, while unavailable work plans only source-supported conditions and result surfaces and records typed `not run` blockers. Preserve the skill contract's evidence provenance, promotion gate, diagnostic and no-file-change boundaries, and write-authority checks. The skill reuses the existing `swarm workers` and `judgment and prose` roles. Discovery is auto-invocable, matching **verify-commands** and **spec-probes**; keep all three `(port addition)` README rows. The engineering method stays here because the loop-governance suite routes to poteto-mode for one.
- **automate-me** and **reflect** cite the authoring playbook as `../poteto-mode/playbooks/authoring-a-skill.md` rather than upstream's prose form. Six references, same target, and the only reason is that `tools/check-skill-content.py` resolves a relative path and cannot see a prose one. These point into `poteto-mode/playbooks/`, which sync moves, so the checked form is what turns a rename into a red CI run instead of six silently stale references. On sync, keep the path form.
- `.claude/settings.json` is fork-only and sets `attribution.sessionUrl` to `false`. Claude Code otherwise appends a `Claude-Session:` trailer carrying a private session URL to commits and pull request bodies made from a cloud or Remote Control session, on by default. That scoping is why only four sessions left traces rather than all of them. Nothing in this repository's skills or tooling caused it and nothing there could suppress it, because the control is a harness setting, which is what this file supplies. It reached 41 commits here across four sessions before anyone noticed and this repository is public, so the history was rewritten and the trailers removed. The file drops only the URL and leaves `Co-Authored-By` intact. Shared project settings outrank user settings in Claude Code's precedence order, so this beats whatever a contributor has in their own `~/.claude/settings.json`; only their `.claude/settings.local.json` or an organization's managed settings outrank it. Being Claude Code specific is not new ground for the port, which already ships `agents/openai.yaml` for Codex and a `.github/` directory. On sync, keep the file.
- `.github/workflows/lint.yml`, `.github/workflows/skill-checks.yml`, `mise.toml`, `tools/check-skill-frontmatter.py`, and `tools/check-cross-suite-references.py` are fork-only CI and local tooling. `mise.toml` includes the task file from `mdsmithaustin/skill-ci` and sets `EVALS_DIR` to the repository-root evals tree, which is what makes the manifest tasks find anything. On sync, keep the file and that variable. `skill-checks.yml` calls the reusable workflow in `mdsmithaustin/skill-ci`. The caller pins one skill-ci commit on the `uses` line. The reusable workflow checks out its own exact revision, and `tools/test_repository_hardening.py` requires one full SHA with no duplicate `skill-ci-ref` input. The existing root GitHub Actions Dependabot entry opens reviewable updates to this pin. Merging an update adopts the runner lock from that skill-ci revision. The caller also passes `evals-dir: evals`, which the same test requires. That input points the shared workflow's `manifests` job at `evals/**/shared-benchmark.json`, where it runs `validate --strict-leakage` and `audit-manifest --fail-on-blockers --strict-judge` with the runner that skill-ci's `runner.lock` pins. Eval manifests and oracles live at the repository root under `evals/<skill>/`, not inside the skill directory. `npx skills` copies a skill directory verbatim to every consumer and offers no exclude mechanism, so anything under `skills/<name>/` ships. `tools/test_eval_artifacts.py` fails when an `evals` or `eval-runs` directory appears anywhere under `skills/`. On sync, keep the input and the lint. The local copies of the frontmatter, content, and PII checkers stay until `skill-checks` passes on `main` and a follow-up deletes them. `tools/check-cross-suite-references.py` enforces the port's independence rule: a skill may name a skill from another suite (Matt Pocock's, agent-loop-runner's, GSD's) only as an optional capability with a stated fallback, or inside an adapter file. The roster of foreign names is `tools/cross-suite-foreign.txt`.

## Canon rules

Rules drawn from the software-design canon (Evans, Fowler, Beck, Martin, and the BDD authors) enter only after a paired screen measures a change in agent behavior. A paired screen runs poteto-mode through `/poteto-mode` or `$poteto-mode` on the same task twice, once with the current skill text and once with the rule added, on Claude Sonnet 5 and on Codex with gpt-6-sol. A repository screen runs in an isolated `sbx` sandbox on a pinned upstream repository. A fixture screen gives the agent a small project of a few files in the prompt. Preserve each owner during sync. Do not reintroduce a rule listed below as not adopted without a new screen.

| Rule | Owner | Source | Screen result |
|---|---|---|---|
| Use the domain's words. Read the nearest `CONTEXT.md`, use its terms, and never use a word it lists under `_Avoid_`. The `_Avoid_` list follows the `CONTEXT.md` format of the optional `domain-modeling` companion. | `principle-model-the-domain` | Evans, [Domain-Driven Design Reference](https://www.domainlanguage.com/ddd/reference/), Ubiquitous Language and Intention-Revealing Interfaces | Repository screen on NousResearch/hermes-agent: 6 of 6 runs passed with the rule and 1 of 6 without, across both agents. |
| Write Given, When, Then tests in the project's existing framework. Do not add Cucumber, a Gherkin runner, or `.feature` files unless the project already runs one. | `principle-test-behavior-not-implementation` | [Cucumber Gherkin reference](https://cucumber.io/docs/gherkin/reference/), [Dan North, Introducing BDD](https://dannorth.net/blog/introducing-bdd/) | Fixture screen: in 4 of 4 pairs where the agent read the rule, 2 per agent, the run without it added a Gherkin runner and `.feature` files and the run with it did not. A project that already ran pytest-bdd kept using it. |
| In review, flag a second name for a concept the code already names. | `principle-model-the-domain` | Evans, [Domain-Driven Design Reference](https://www.domainlanguage.com/ddd/reference/), Ubiquitous Language | Admitted for review with the Code review playbook, see below. |
| In review, flag one word's different concepts combined into one type. | `principle-model-the-domain` | Evans, Bounded Context; [Fowler, BoundedContext](https://martinfowler.com/bliki/BoundedContext.html) | Admitted for review. The build-time version with "merge within one context" stays rejected. |
| In review, list a shared symbol's callers and flag a change for one request that alters another business function's behavior. | `principle-model-the-domain` | [Martin, The Single Responsibility Principle](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html) | Admitted for review. |
| In review, flag a domain or policy module that imports a framework, driver, ORM, IO library, generated schema, or adapter module. | `principle-boundary-discipline` | [Martin, The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html) | Admitted for review. |
| Smells a diff can show, each with a refactoring to suggest and a condition to leave it. | `poteto-mode/references/review-lens.md` | Fowler and Beck, *Refactoring* 2nd ed., chapter 3, and the [refactoring catalog](https://refactoring.com/catalog/) | Admitted for review. |

Review screen. The Code review playbook, its review lens, and the five review rows above entered together. A repository screen seeded six flawed pull requests and two clean controls on the pinned omnigent and hermes-agent commits. A judge from the other model family, calibrated on labeled sample reviews for every case, graded each review. With the playbook, Claude Sonnet 5 fully found the flaw in 9 of 12 reviews and at least partly found it in 12 of 12, against 6 of 12 and 9 of 12 without it. Codex with gpt-6-sol read the playbook and the leaves in every run and found 1 of 12, at least partly 2 of 12, against 0 of 12 and 1 of 12 without it. Admission rests on the Claude result. Neither agent raised a false alarm on the controls. The review rules are scoped to review in their leaves, so their effect on building stays unmeasured.

Not adopted. Each reason is a measured result unless it says otherwise.

- Separate types per bounded context with "merge within one context" (Evans), repository screen: Codex merged unrelated families in 5 of 6 runs with the rule and 0 of 3 without. Claude passed either way.
- A widened `principle-model-the-domain` when-clause and a Feature step 2 shape pointer, repository screen: 3 of 6 runs passed, against 6 of 6 for the leaf rule alone.
- One name per concept (Evans) as a build rule, repository screen: Claude passed 3 of 3 without it. Codex rose from 0 of 3 to 1 of 3. It is adopted for review only.
- A `domain-modeling` route at Feature step 1, repository screen: no run added a glossary term. A `codebase-design` route at Refactoring step 3: the runs without it passed 12 of 12.
- Preparatory refactoring at Feature step 3 (Beck, Fowler), repository screen: no run restructured first, with or without the rule.
- Fixture screens only, where the runs without the rule already behaved correctly or the rule did not change the result: anti-corruption layer, invariant owner, and value types (Evans), two hats, commit order, and branch by abstraction (Fowler), and Given, When, Then shape and domain test names (BDD). A repository screen can still admit any of them.
- Rule text in the always-loaded poteto-mode index, a design decision rather than a measurement: text there reaches every session and turns the index from a router into a rulebook. A rule's trigger belongs in an index when-clause or a playbook step, and its text belongs in the leaf.

## Named-agent portability

Root `agents/*.md` owns upstream persona text and metadata. `tools/generate-subagents.py` owns the explicit port mapping and generates `skills/pstack-harness/references/subagents/roles.json`. The installed `pstack-harness/scripts/subagents.py` reads this bundle without Git, network access, or a source checkout. Do not hand-edit generated payloads.

Native Claude wrappers use normalized names and translate upstream `is_background` to `background`. Codex wrappers use TOML with `name`, `description`, and `developer_instructions`. Both contain complete persona briefings and installed skill paths. They leave model, effort, tool, and sandbox policy unset. Comment Sicko may edit comments; preserve its ban on application-code edits. Hermes has no confirmed arbitrary custom-agent-file loader, so its delegate receives the complete briefing through context.

The named-role contract preserves the aliases `poteto-agent` and `Comment Sicko`. A native registration requires generated bytes that match the briefing rendered from the current skills root, or from an alias root whose named `SKILL.md` files resolve to the same files. It also requires live catalog confirmation. Otherwise generic native delegation, own-CLI subprocesses, and sequential arms receive the same full persona. Keep the configured arm count and existing model policy. Native installation is optional, uses an explicit project or user destination, and refuses user-managed or edited role files. Payload checks never claim actual native activation.

After every upstream agent change, run `python3 tools/generate-subagents.py`. Failure signal: nonzero exit for unsupported source input. Then run `python3 tools/generate-subagents.py --check`. Failure signal: nonzero exit for source-to-bundle drift. Commit the upstream source and generated payload together. Reapply the named-role callsite and setup instructions during sync.

Run `python3 -m unittest discover -s tools -p 'test_subagents.py'` with Python 3.12. Failure signal: nonzero exit or zero collected tests. Run `python3 tools/probe-subagent-install.py` for actual pinned project installations with symlinks and copies. Failure signal: nonzero exit; the JSON report identifies the failed case. The probe uses temporary roots and never registers roles into the user's real configuration. Native loader and child-behavior checks require separate live-session evidence.

## What deliberately did not change

- Skill bodies, playbooks, and principles retain upstream engineering content except for the substitutions and port additions recorded above.
- Frontmatter extras (`mode`, `icon`, `color`, `reminder`, `disable-model-invocation`): Cursor-flavored but harmless; CLIs that don't know a key ignore it.
- `agents/` remains unchanged upstream text. The port generates an installed bundle and native wrappers from it, as described above.

## Syncing from upstream

The upstream sync workflow is available through the manual-dispatch GitHub Action in `.github/workflows/upstream-sync.yml`. Local schedules, machine paths, logs, and maintainer-specific tooling are intentionally not documented in this repository.

Manually:

1. `git remote add upstream https://github.com/cursor/plugins.git` (sparse-checkout `pstack`).
2. Diff upstream's `pstack/` against the SHA in `.github/upstream-sha` (originally the import commit).
3. Reapply the substitution map to the incoming hunks, keep the port additions intact, regenerate and check the role bundle, and bump `.github/upstream-sha`.
